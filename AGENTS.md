# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Что это за репозиторий

`roxy` — это набор кастомных Claude Code скилов, реализующих фиче-ориентированный процесс агентной разработки. Здесь нет приложения, сборки и тестового рантайма: артефакты — markdown-файлы скилов. «Тестирование» скила = запуск его на пилотной фиче в реальном проекте.

Скилы создаются из глобально установленных скилов `~/.agents/skills` мета-скилом `forge` и адаптируются под рабочий процесс пользователя.

## Структура скила

Каждый скил — папка `skills/{name}/`:

- `SKILL.md` — обязателен. YAML frontmatter (`name`, `description`, опц. `argument-hint`) + тело инструкции.
- `references/*.md` — опциональные материалы, подгружаемые по требованию из этапов `SKILL.md`.

`description` во frontmatter — главный механизм триггеринга: содержит «что делает» + явные триггер-фразы пользователя. Frontmatter написан простым языком, коротко (не более 200 символов) и понятно, без технических терминов. Триггер-фразы только на русском.

## Конвейер разработки (порядок скилов)

Скилы выстроены в цепочку этапов работы над проектом и фичами:

1. `initialize` — фиксирует контекст проекта в `./workflow/` и создает базовые файлы для дальнейшей работы.
2. `architecture` — подбирает и фиксирует архитектурный паттерн (`ARCHITECTURE.md`).
3. `design-guideline` — извлекает и фиксирует гайдлайн по дизайну проекта (`DESIGN.md`).
4. `roadmap` — фиксирует текущие цели и дорожную карту (`VISION.md` и `ROADMAP.md`).
5. `feature` — поверхностно фиксирует идею фичи (`feature.md`).
6. `planning` — превращает фичу в подробный план (`plan.md`).
7. `design` — дополняет план рекомендациями по дизайну (`design.md`).
8. `improve` — повторный глубокий анализ и переписывание `plan.md`.
9. `task` — разбивает план на самодостаточные задачи (`NN-task.md`).
10. `implement` — выполняет работу по фиче (по таскам / по фазам / напрямую по `feature.md`, если задача простая и плана нет).
11. `test` — покрывает реализованную фичу тестами (`tests.md`), пишет тестовый код и запускает тесты.
12. `docs` — пишет документацию с нуля или обновляет текущую документацию на основе реализованной фичи в `./docs/{concept,spec,tech}/`.
13. `audit` — анализирует кодовую базу и документы, дает рекомендации отчётом в чат, файлы не правит.
14. `markov` — прямая реализация законов Маркова для одного локального документа: принимает путь, итеративно применяет к нему каждый закон, поднимает нужный контекст и переписывает переданный документ.
15. `whoami` — наделяет агента душой Рокси Мигурдии (`SOUL.md`)

`forge` стоит особняком — это мета-скил, собирающий остальные скилы.
`markov` тоже стоит особняком: это не аудит и не генератор рекомендаций, а инструмент нормализации конкретного документа по законам Маркова.
`whoami` так же стоит особняком: не связан с проектной разработкой, он создает в корне проекта файл `SOUL.md`.

## Структура `./workflow/` (целевые проекты, не этот репозиторий)

Скилы создают и обновляют единую структуру в проектах пользователя:

```
./workflow/
├── PLAN.md          # общий статус фич + «хвосты» для дальнейшего разбора
├── VISION.md        # идеологическое видение
├── ROADMAP.md         # цели разработки
├── ARCHITECTURE.md  # архитектура
├── PROJECT.md       # тех-стек, запуск, деплой
├── DESIGN.md        # описание brand|design-guideline
├── archive/         # закрытые фичи
└── features/{slug}/
    ├── feature.md   # описание фичи
    ├── plan.md      # план с чекбоксами задач
    ├── design.md    # дизайн (если применимо)
    ├── tests.md     # описание тестов
    └── NN-task.md   # задачи после разбивки плана
```

Каждый скил в финале своей работы обновляет статус фичи в `./workflow/PLAN.md` (статусы: `[ ]` новая, `[-]` спланирована, `[+]` разбита на задачи, `[x]` выполнена, `[*]` протестирована, `[/]` в архиве).

## Принципы (обязательны при правке любого скила)

`markov-laws.md` (корень) и `skills/forge/references/markov-laws.md` — свод «законов Маркова» для агентной разработки. При написании и правке скилов добавляй их **как естественные требования внутри инструкций** — без упоминания «закона», номеров или ссылок на свод:

- **Достаточное настоящее.** Скил и его артефакты самодостаточны: исполнитель видит только текущее состояние, без биографии создания.
- **Без биографии и дельт.** Никаких «раньше X, теперь Y», «после рефакторинга», «теперь можно». Снятое правило просто отсутствует.
- **Тесты — про инвариант, не про инцидент.** Не покрывать очевидное, не писать тесты «что-то удалено».

Исключение — запланированный `markov`: он прямо работает с законами, поэтому его `SKILL.md` должен содержать полный свод законов как рабочую базу. На вход `markov` принимает локальный путь к документу, читает документ, при необходимости поднимает локальный контекст, затем проходит по законам итеративно: для каждого закона определяет применимость, правит смысл и структуру документа, удаляет биографию и дельты, нормализует канон, переименовывает тестовые формулировки в инварианты, убирает операционный мусор. Результат — обновлённый переданный документ, не отдельный отчёт.

## Конвенции скилов, создаваемых `forge`

- Тело `SKILL.md` — на языке пользователя (русский). Имена скилов, MCP, инструментов, путей, ключей frontmatter, команд — в оригинале.
- `mcp__sequential-thinking__sequentialthinking` обязателен на аналитических этапах для типов: создание фичи, планирование, разбивка на задачи, улучшение плана, документирование, анализ.
- Правила сжатия финального артефакта встраиваются в `SKILL.md` отдельной секцией (без внешних вызовов и без имени «caveman»).
- Запрет git-операций встраивается в каждый создаваемый скил.
- Стиль инструкций: императив («прочитай X», «запиши Y»), конкретные полные имена путей и инструментов, «почему» там, где не очевидно.

## Git

Рабочее дерево всегда грязное — пользователь и параллельные агенты вносят правки одновременно. Не проверяй статус git, не создавай ветки и коммиты без явной просьбы. Коммиты и ветки делает пользователь сам.
