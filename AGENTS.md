## Что это за репозиторий

`roxy` — набор кастомных Claude Code скилов, реализующих фиче-ориентированный процесс агентной разработки. Здесь нет приложения, сборки и тестового рантайма: артефакты — markdown-файлы скилов. «Тестирование» скила = запуск его на пилотной фиче в реальном проекте.

## Философия скилов

Скил направляет компетентного агента, а не диктует каждое действие. Современные модели хорошо понимают намерение, если базовые инструкции даны качественно, поэтому скил фиксирует цель этапа, его границы, формат артефакта и нетривиальные ограничения — без микроменеджмента, исчерпывающих таксономий и чек-листов очевидного.

То же относится к порождаемым артефактам (`feature.md`, `plan.md`, `NN-task.md`, `design.md`, `tests.md`): они объясняют, чего хочет пользователь, и направляют исполнителя. Размер артефакта пропорционален сложности фичи; для простой фичи пары предложений достаточно.

Эталон стиля SKILL.md — `skills/markov/SKILL.md`: лаконичный английский полными предложениями, императив, конкретные пути, «почему» только там, где это влияет на исполнение.

## Структура скила

Каждый скил — папка `skills/{name}/`:

- `SKILL.md` — обязателен. YAML frontmatter (`name`, `description`) + тело инструкции на английском.
- `README.md` — человекочитаемая карточка скила на русском: назначение, место в конвейере, входы, выходы, границы. Для `forge` README одновременно служит каноном намерений при пересборке скила. README не должен расходиться со SKILL.md.

`description` во frontmatter — главный механизм триггеринга: «что делает» + явные триггер-фразы, простым английским, до ~200 символов.

## Конвейер разработки

Скилы выстроены в цепочку. Каждый скил знает своё место, держит границу своего этапа и завершает работу рекомендацией следующего шага, выведенной из фактического состояния. Скилы не вызывают друг друга автоматически.

1. `initialize` — создаёт `./workflow/`, фиксирует тех-контекст (`PROJECT.md`), сеет хвосты в `PLAN.md`.
2. `roadmap` — видение и дорожная карта (`VISION.md`, `ROADMAP.md`).
3. `architecture` — архитектурный канон (`ARCHITECTURE.md`).
4. `design-guideline` — визуальный канон (`DESIGN.md`).
5. `feature` — исследует запрос, задаёт вопросы до записи, создаёт человекочитаемый бриф (`feature.md`). Простая фича может идти сразу в `implement`, UI-фича — через `design`.
6. `planning` — для задач, которые трудно обработать за раз: компактный план с фазами (`plan.md`).
7. `design` — выборочно, для нового и сложного UX/UI: компактные дизайн-решения (`design.md`).
8. `improve` — проверочный проход по плану сложной или архитектурно важной фичи (часто другой моделью): точечные правки без смены структуры плана.
9. `task` — разбивает большой план на самодостаточные `NN-task.md`, превращая `plan.md` в компактную карту: при имплементации агент читает карту и одну задачу, не весь план.
10. `implement` — реализует одну задачу/фазу/простую фичу; в финале closing sweep: уборка осиротевшего кода и нормализация затронутого через дисциплину `markov`. Тесты и доки не пишет.
11. `test` — покрывает фичу тестами инвариантов (`tests.md`), сверяет соседние тесты с реальностью.
12. `docs` — документация текущего состояния (`README.md`, `./docs/{concept,spec,tech}/`), сверяет связанные страницы.
13. `audit` — read-only анализ, рекомендации отчётом в чат, файлы не правит.
14. `markov` — нормализация указанной цели по законам Маркова; стоит особняком, используется и как финальная проверка `implement`/`test`/`docs`.
15. `whoami` — вселяет душу: создаёт `SOUL.md` (по умолчанию — образ Рокси Мигурдии, канон встроен в скил) и подключает его строкой в `AGENTS.md`/`CLAUDE.md`; вне проектного конвейера.

`forge` стоит особняком — мета-скил: пересобирает `SKILL.md` скила по его `README.md` и конвенциям этого репозитория.

## Структура `./workflow/` (целевые проекты, не этот репозиторий)

```
./workflow/
├── PLAN.md          # статусы фич + активные хвосты
├── VISION.md        # видение
├── ROADMAP.md       # цели разработки
├── ARCHITECTURE.md  # архитектура
├── PROJECT.md       # тех-стек, запуск, деплой
├── DESIGN.md        # визуальный канон
├── archive/         # закрытые фичи
└── features/{slug}/
    ├── feature.md   # бриф фичи
    ├── plan.md      # план; после task — компактная карта задач
    ├── design.md    # дизайн (если применимо)
    ├── tests.md     # карта инвариантов и верификация
    └── NN-task.md   # самодостаточные задачи
```

Статусы фич в `./workflow/PLAN.md`: `[ ]` новая, `[-]` спланирована, `[+]` разбита на задачи, `[x]` реализована, `[*]` протестирована, `[/]` в архиве. Каждый фиче-скил в финале обновляет только строку своей фичи.

## Принципы (обязательны при правке любого скила)

`markov-laws.md` (корень) — свод законов Маркова для агентной разработки. При написании и правке скилов встраивай их **как естественные требования внутри инструкций** — без упоминания «закона», номеров или ссылок на свод:

- **Достаточное настоящее.** Скил и его артефакты самодостаточны: исполнитель видит только текущее состояние, без биографии создания.
- **Без биографии и дельт.** Никаких «раньше X, теперь Y», «после рефакторинга», «теперь можно». Снятое правило просто отсутствует.
- **Тесты — про инвариант, не про инцидент.** Не покрывать очевидное, не писать тесты «что-то удалено».
- **Забывание — это обслуживание.** Устаревшие артефакты и правила удаляются, а не помечаются.

Исключение — `markov`: он прямо работает с законами, его `SKILL.md` содержит полный свод как рабочую базу.

## Конвенции SKILL.md

- Тело — на английском. Имена скилов, инструментов, путей, ключей frontmatter, команд — в оригинале.
- Каждый `SKILL.md` содержит стандартный `## Language Notice`: проектные артефакты пишутся на рабочем языке целевого проекта.
- Никаких MCP-инструментов размышления: аналитические шаги — обычные шаги рассуждения.
- Запрет git-операций встраивается в каждый скил одной строкой.
- Вопросы пользователю — батчем, до записи артефакта, рекомендованный вариант первым с пометкой «(Recommended)». В записанных артефактах не остаётся вопросов, которые можно было закрыть диалогом.
- Финальный отчёт скила заканчивается рекомендацией следующего шага конвейера (кроме `audit`, `markov`, `whoami`, `forge`).
- Стиль инструкций: императив («Read X», «Write Y»), конкретные полные пути, «почему» там, где не очевидно.
- Шаблоны артефактов — минимальное ядро секций; секция добавляется, только если несёт решение.

## Git

Рабочее дерево всегда грязное — пользователь и параллельные агенты вносят правки одновременно. Не проверяй статус git, не создавай ветки и коммиты без явной просьбы. Коммиты и ветки делает пользователь сам.
