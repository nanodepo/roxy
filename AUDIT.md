# Аудит границ ответственности скилов

Дата: 2026-05-16

## Контекст

В репозитории есть противоречия между текущими `SKILL.md`, конвейером в `AGENTS.md` и запланированными скилами. Главные примеры:

- `initialize` создаёт `VISION.md` и `GOALS.md`, хотя это зона будущего `roadmap`.
- `planning` и `improve` создают или переписывают `tests.md`, хотя тестовый план должен принадлежать `test`.
- `forge` закрепляет старые правила генерации, поэтому точечные правки отдельных скилов будут снова воспроизводить те же противоречия.

Этот документ фиксирует текущее состояние и рекомендуемую целевую модель.

## Категории скилов

### Проектный уровень

Скилы, которые фиксируют канон проекта целиком и не работают с отдельной фичей как основной единицей:

- `initialize`
- `roadmap`
- `architecture`
- `design-guideline`
- `docs`

`docs` сейчас пограничный: в `AGENTS.md` он стоит после тестов как фичевый этап, но реальный `skills/docs/SKILL.md` создаёт проектный `README.md` и `./docs/{concept,spec,tech}/`.

### Работа по фиче

Скилы, которые работают внутри `./workflow/features/{slug}/` и двигают фичу по жизненному циклу:

- `feature`
- `planning`
- `design`
- `improve`
- `task`
- `implement`
- `test`

### Другие

Скилы вне обычной линейной разработки фичи:

- `forge` — мета-скил для создания других скилов.
- `audit` — запланированный скил для анализа и рекомендаций.
- `markov` — запланированный скил для прямого применения законов Маркова к одному переданному документу.
- `whoami` — позволяет создать файл SOUL.md который описывает душу агента. 

## Зоны ответственности: как есть и как должно быть

| Скил | Как есть сейчас | Как должно быть |
|---|---|---|
| `initialize` | Создаёт `VISION.md`, `GOALS.md`, `PROJECT.md`, `PLAN.md`. | Только bootstrap: `./workflow/`, `PROJECT.md`, базовый `PLAN.md`, хвосты на `roadmap`, `architecture`, `design-guideline`. Не пишет `VISION.md` и `GOALS.md`. |
| `roadmap` | Запланирован в `AGENTS.md`, но скила нет. | Единственный владелец `VISION.md` и `GOALS.md`: видение, цели, дорожная карта, приоритеты. |
| `architecture` | Создаёт `ARCHITECTURE.md`, читает проектный контекст, обновляет хвосты в `PLAN.md`. | Оставить почти как есть. Только читать `VISION.md` / `GOALS.md` / `PROJECT.md`, писать `ARCHITECTURE.md` и хвосты. |
| `design-guideline` | Создаёт `./workflow/DESIGN.md`: извлекает визуальный язык из кода или собирает опросом, обновляет хвосты в `PLAN.md`. | Оставить. Единственный владелец `./workflow/DESIGN.md`: бренд, визуальные принципы, UI-конвенции. |
| `feature` | Создаёт только `feature.md` и регистрирует фичу в `PLAN.md` со статусом `[ ]`. | Оставить. Может читать `DESIGN.md`, но не создаёт дизайн, тесты или план. |
| `planning` | Создаёт `plan.md` и `tests.md`. | Только `plan.md`: фазы, задачи, файлы, зависимости, риски, открытые вопросы. Не создаёт `tests.md`. |
| `design` | Запланирован в `AGENTS.md`, но скила нет. `implement` и `improve` уже учитывают `design.md`. | Единственный владелец `./workflow/features/{slug}/design.md`: UI/UX решения конкретной фичи на основе проектного `DESIGN.md`. |
| `improve` | Улучшает и переписывает `plan.md` и `tests.md`. | Улучшает только `plan.md`. Тестовые замечания фиксирует хвостом для `test`. |
| `task` | Разбивает фазы `plan.md` на `NN-task.md`, переписывает `plan.md` как карту фичи, тесты не трогает. | Оставить. Владелец декомпозиции и переписанного `plan.md`-навигатора. |
| `implement` | Реализует код, переключает чекбоксы в `plan.md`, не читает `tests.md`, но разрешает прямую реализацию по `feature.md`. | Код + чекбоксы. Если `plan.md` отсутствует, допускается реализация напрямую по `feature.md` для простых задач. |
| `test` | Создаёт/расширяет `tests.md` и пишет код тестов, но тесты не запускает автоматически. | Единственный владелец `tests.md` и тестового кода. Пишет тесты и запускает их командой из `PROJECT.md` или обнаруженного тестового фреймворка. |
| `docs` | Делает проектный `README.md` и `./docs/{concept,spec,tech}/`; содержит mini-audit режим существующей документации. | Пишет документацию с нуля или обновляет текущую документацию на основе реализованной фичи. Audit вынести в `audit`. |
| `audit` | Запланирован в `AGENTS.md`, но скила нет. | Только анализ и отчёт в чат. Не правит код, документы и workflow-артефакты. |
| `markov` | Запланирован в `AGENTS.md`, но скила нет. | Прямая реализация законов Маркова: принимает локальный путь к документу, содержит полный свод законов, итеративно применяет каждый закон к документу, при необходимости поднимает контекст и переписывает переданный документ. |
| `forge` | Генерирует старую модель: `initialize` владеет `VISION.md` / `GOALS.md`; `planning` и `improve` владеют `tests.md`. | Обновить первым: матрицу артефактов, спец-указания и структуру `workflow`, иначе новые скилы снова будут неправильными. |

## Найденные проблемы

### 1. Конфликт `initialize` и `roadmap`

`initialize` сейчас создаёт:

- `./workflow/VISION.md`
- `./workflow/GOALS.md`
- `./workflow/PROJECT.md`
- `./workflow/PLAN.md`

Но `AGENTS.md` вводит отдельный этап `roadmap`, который должен фиксировать `VISION.md` и `GOALS.md`.

Риск: два владельца идеологического и целевого канона проекта. Дальше агенты будут либо перезаписывать чужую зону, либо не понимать, какой скил запускать.

### 2. Конфликт `planning`, `improve` и `test` за `tests.md`

`planning` создаёт `tests.md`, `improve` переписывает `tests.md`, `test` расширяет `tests.md` и пишет код тестов.

Риск: тестовый план появляется до реализации и до анализа фактических изменений. `test` получает не свой черновик как канон, а `improve` может менять тестовый домен без владения тестовой стадией.

### 3. `forge` закрепляет противоречия

В `forge` матрица применимости и спец-указания всё ещё говорят:

- `initialize` → `VISION.md`, `GOALS.md`, `PROJECT.md`
- `planning` → `plan.md`, `tests.md`
- `improve` → `plan.md`, `tests.md`

Риск: даже после ручной правки отдельных скилов новые скилы, созданные через `forge`, снова получат старые границы.

### 4. Скил `design` отсутствует

Проектный `design-guideline` реализован: `skills/design-guideline/SKILL.md` с `references/design-sources.md` — единственный владелец `./workflow/DESIGN.md`.

В `AGENTS.md` заявлен фичевый скил `design` → `./workflow/features/{slug}/design.md`, но реальной папки `skills/design/` нет. При этом `implement` уже читает `design.md`, а `improve` учитывает его как вход.

Риск: фичевый дизайн может быть прочитан и учтён, но в текущем конвейере его некому создать.

### 5. `docs` смешан с `audit`

`docs` проверяет существующую документацию и предлагает audit-режим, хотя `audit` заявлен отдельным этапом.

Риск: документация начинает выполнять роль проверки и отчёта. Это размывает чистую передачу: `docs` должен фиксировать текущее состояние, `audit` — находить расхождения.

### 6. Статус `[*]` требует запуска тестов

В `PLAN.md` статус `[*]` описан как «покрыта тестами и протестирована». Поэтому `test` должен не только писать тесты, но и запускать их.

Риск текущего состояния: статус сообщает больше, чем скил реально сделал.

### 7. `implement` допускает прямую реализацию без плана

`implement` разрешает режим C: имплементация напрямую по `feature.md`.

Решение: режим допустим для простых задач, где отдельный `plan.md` избыточен. Для сложных задач скил должен объяснить риск и предложить сначала выполнить `planning`.

### 8. Нет прямого инструмента нормализации документа по законам Маркова

`audit` задуман как анализ и рекомендации, а `forge` растворяет применимые принципы в новых скилах. Но нет отдельного скила, который берёт уже существующий документ и прямо переписывает его по полному своду законов.

Риск: документы можно проверить, но нельзя единообразно нормализовать. Агент снова будет править по памяти и вкусу, а не по пошаговой процедуре: закон → применимость → контекст → правка → следующий закон.

## Рекомендуемый канон артефактов

Один артефакт — один владелец:

| Артефакт | Владелец |
|---|---|
| `./workflow/PLAN.md` | общий индекс; каждый скил обновляет только свою строку статуса и хвосты |
| `./workflow/PROJECT.md` | `initialize` |
| `./workflow/VISION.md` | `roadmap` |
| `./workflow/GOALS.md` | `roadmap` |
| `./workflow/ARCHITECTURE.md` | `architecture` |
| `./workflow/DESIGN.md` | `design-guideline` |
| `./workflow/features/{slug}/feature.md` | `feature` |
| `./workflow/features/{slug}/plan.md` | `planning`, затем `improve`, затем `task` как нормализация в карту фаз |
| `./workflow/features/{slug}/design.md` | `design` |
| `./workflow/features/{slug}/NN-task.md` | `task` |
| код проекта | `implement` |
| `./workflow/features/{slug}/tests.md` | `test` |
| код тестов | `test` |
| `README.md`, `./docs/{concept,spec,tech}/` | `docs` |
| audit-отчёт в чат | `audit` |
| любой переданный документ, который нужно нормализовать по законам Маркова | `markov` |
| новые `SKILL.md` | `forge` |

## Рекомендуемый порядок исправления

1. Обновить `AGENTS.md` как верхний канон: категории скилов, владельцы артефактов, порядок конвейера.
2. Обновить `skills/forge/SKILL.md`: матрицу артефактов, спец-указания по типам, описание структуры `./workflow/`.
3. Переписать `skills/initialize/SKILL.md`: оставить `PROJECT.md` и bootstrap, убрать `VISION.md` / `GOALS.md`.
4. Создать `skills/roadmap/SKILL.md`: владелец `VISION.md` / `GOALS.md`.
5. Переписать `skills/planning/SKILL.md`: убрать создание `tests.md`.
6. Переписать `skills/improve/SKILL.md`: убрать работу с `tests.md`.
7. Переписать `skills/test/SKILL.md`: сделать его единственным владельцем `tests.md`; решить вопрос запуска тестов и статуса `[*]`.
8. Создать `skills/design-guideline/SKILL.md`: владелец проектного `DESIGN.md`. **Реализован.**
9. Создать `skills/design/SKILL.md`: владелец фичевого `design.md`.
10. Переписать `skills/docs/SKILL.md`: скил пишет документацию с нуля или обновляет текущую на основе реализованной фичи; audit-режим убрать.
11. Создать `skills/audit/SKILL.md`: анализ и рекомендации только в чат, без правки файлов.
12. Создать `skills/markov/SKILL.md`: прямое применение полного свода законов Маркова к локальному документу.
13. Пересмотреть `skills/implement/SKILL.md`: сохранить прямую реализацию по `feature.md` для простых задач без плана.

## Целевая цепочка

```text
initialize
→ roadmap
→ architecture
→ design-guideline
→ feature
→ planning
→ design
→ improve
→ task
→ implement
→ test
→ docs
→ audit
→ markov (по требованию, для нормализации конкретного документа)
```

`forge` стоит отдельно и должен создавать скилы по этой модели.
`markov` тоже стоит отдельно: его вызывают для конкретного документа, когда нужен глубокий структурный и смысловой проход по законам Маркова.

## Принятые решения

1. `docs` остаётся одним скилом: пишет документацию с нуля или обновляет текущую на основе реализованной фичи.
2. `test` пишет тесты и запускает их.
3. `implement` сохраняет режим прямой реализации по `feature.md`, потому что для простых задач отдельного плана может не быть.
4. `audit` делает анализ и даёт отчёт в чат, без записи файлов.
5. `markov` принимает только локальные пути.

## Черновой контракт `markov`

`markov` — скил для прямой реализации законов Маркова в существующем документе.

### Вход

```text
<document-path>
```

Документ может быть `AGENTS.md`, `SKILL.md`, `AUDIT.md`, `README.md`, файл из `./workflow/` или другой markdown-документ. Вход — только локальный путь. Внешние ссылки не поддерживаются.

### Обязательное содержимое скила

`skills/markov/SKILL.md` должен содержать полный свод законов Маркова как рабочую базу, потому что этот скил прямо применяет законы, а не растворяет их в других инструкциях.

### Процедура

1. Прочитать переданный документ.
2. Определить тип документа: инструкция агента, скил, план, тестовый план, документация, аудит, README, другое.
3. Поднять нужный локальный контекст: соседние файлы, `AGENTS.md`, `markov-laws.md`, связанные workflow-артефакты, если без них нельзя понять текущий канон.
4. Запустить глубокий анализ через `mcp__sequential-thinking__sequentialthinking`.
5. Пройти по законам итеративно. Для каждого закона:
   - определить, применим ли он к этому типу документа;
   - найти фрагменты, которые нарушают закон;
   - понять, нужен ли дополнительный контекст;
   - переписать документ так, чтобы он описывал текущее состояние без биографии, дельт и операционного мусора;
   - сохранить смысловые инварианты, а не эпизоды.
6. После прохода по всем законам сделать финальную сверку: документ самодостаточен, каноничен, не хранит лишнюю историю, не смешивает аудит с инструкцией, тестовые формулировки говорят об инвариантах.
7. Обновить тот же документ, который был передан на вход.
8. Сообщить пользователю коротко: какие классы проблем исправлены, какие фрагменты оставлены без изменений и почему.

### Границы

- `markov` не создаёт отдельный отчёт вместо правки документа.
- `markov` не меняет код проекта.
- `markov` не делает git-операции.
- `markov` не переписывает связанные документы автоматически: если проблема найдена за пределами входного файла, он фиксирует это в ответе пользователю.
