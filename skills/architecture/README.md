# architecture

## Назначение

`architecture` выбирает и фиксирует архитектурный канон проекта. Скил отвечает только за архитектурный паттерн, границы модулей и правила размещения кода.

## Ответственность

- Проанализировать текущую структуру проекта.
- Прочитать `PROJECT.md`, `VISION.md` и `ROADMAP.md`, если они есть.
- Создать или обновить `./workflow/ARCHITECTURE.md`.
- Добавить в `PLAN.md` только служебные архитектурные хвосты, если решения требуют последующих работ.

## Связь с конвейером

`architecture` работает после `initialize` и желательно после `roadmap`. Его канон читают `planning`, `improve`, `task`, `implement`, `test` и `docs`.

## Почему граница такая

Архитектура задаёт правила размещения и зависимости кода, но не должна сама выполнять рефакторинг. Так решение остаётся каноном, а исполнение уходит в фичевые этапы; хвосты в `PLAN.md` только указывают на будущую работу.

## Входной контекст

- `./workflow/PROJECT.md`
- `./workflow/VISION.md`
- `./workflow/ROADMAP.md`
- структура исходного кода
- существующие архитектурные документы, если они есть

## Выходные артефакты

- `./workflow/ARCHITECTURE.md`
- служебные архитектурные хвосты в `./workflow/PLAN.md`

## Не делает

- Не пишет код.
- Не реализует рефакторинг.
- Не создаёт фичевые планы.
- Не пишет тесты.
- Не делает git-операции.

## Критерий готовности

Агент, реализующий фичу, понимает, куда класть код, какие границы не нарушать и какой архитектурный стиль является текущим каноном.
