# REFERENCES — исследование внешних скилов для `architecture`

## Метод

Через `find-skills` (`npx skills find`) собраны скилы экосистемы `skills.sh`, близкие по сути к нашему `architecture` — фиксация архитектурного канона, выбор паттерна, границы модулей, правила размещения кода. Каждый кандидат разобран на предмет того, что усилит наш скил, не выйдя за его границы (один артефакт `ARCHITECTURE.md` + архитектурные хвосты в `PLAN.md`; скил не пишет код, не рефакторит, не ведёт историю решений).

## Принятые усиления

Четыре блока делают расплывчатые шаги текущей инструкции операциональными и при этом не выходят за границы скила и принципы (достаточное настоящее, без биографии и дельт).

### A. Компактный каталог архитектурных паттернов

Дать в `SKILL.md` короткий справочный список паттернов с условиями применимости, чтобы выбор опирался на опоры, а не изобретался: Layered, Modular monolith, Clean / Hexagonal, DDD (стратегический), Microservices, Event-driven, MVVM / MVU (для UI), Serverless. Для каждого — одна строка «когда уместен». Без кода.
Источник: `architecture-patterns`, `architecture-blueprint-generator`.

### B. Метод авто-детекта текущего паттерна

Заменить общее «проанализировать структуру проекта» на конкретные эвристики: имена и вложенность директорий, направление зависимостей между слоями, где лежит бизнес-логика, есть ли явные границы (адаптеры, порты, модули). По эвристикам скил формулирует, какой паттерн фактически действует сейчас, и только потом решает — закрепить его или сменить.
Источник: `architecture-blueprint-generator`.

### C. Чек-лист секций `ARCHITECTURE.md`

Зафиксировать обязательный состав канона, чтобы фичевый агент гарантированно получал ответы:
- выбранный паттерн и краткое обоснование (1–2 строки);
- границы модулей и правила зависимостей (что от чего может зависеть);
- правила размещения кода (куда класть новый код);
- cross-cutting concerns: аутентификация, обработка ошибок, логирование, валидация, конфигурация;
- конвенции именования и структуры.
Источник: `architecture-blueprint-generator`.

### D. Лёгкая методология выбора

При выборе паттерна сверять кандидатов с контекстом проекта — масштаб, размер команды, цели из `ROADMAP.md` — и фиксировать обоснование как 1–2 строки канона рядом с паттерном. Это закрепляет «почему граница такая» как часть текущего состояния.
Источник: `architecture-decision`, `architecture-decision-records`.

## Сознательно отклонено

| Что | Источник | Причина |
|---|---|---|
| Код-примеры на конкретных языках/фреймворках | `architecture-patterns` | Скил не пишет код; перегружает канон-документ |
| ADR с жизненным циклом статусов (proposed / accepted / deprecated / superseded) | `architecture-decision-records` | Прямой конфликт с принципом «без биографии и дельт» — канон хранит только текущее решение |
| Генерация диаграмм C4 / UML / Mermaid как ядро скила | `architecture-blueprint-generator` | Тяжёлая машинерия; допустимо лишь опционально, не обязательным шагом |
| Параллельная генерация альтернатив и оформление RFC | `improve-codebase-architecture` | Это домен скила `improve`, а не фиксации канона |
| Оценка и учёт технического долга | `architecture-decision` | Это домен скила `audit` |
| Аппарат Ousterhout (deep modules, seams, leverage) | `improve-codebase-architecture` | Оценочная линза рефакторинга; максимум одна фраза как критерий «хорошей границы», не отдельный аппарат |
