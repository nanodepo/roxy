# Архитектурные паттерны — справочник

Справочный материал. Скил `architecture` читает этот файл на этапе оценки и рекомендации. В артефакт `./workflow/ARCHITECTURE.md` содержимое напрямую не копируется — даёт основу, финальный документ адаптируется под язык и стек проекта.

## Decision Matrix

| Фактор | Layered | Clean Architecture | Modular Monolith | DDD | Microservices |
|--------|---------|-------------------|-------------------|-----|---------------|
| Размер команды | 1–5 | 1–15 | 5–30 | 5–30 | 20+ |
| Сложность домена | Низкая | Средняя–Высокая | Средняя–Высокая | Высокая | Высокая |
| Требования к масштабу | Низкие | Умеренные | Умеренные–Высокие | Умеренные–Высокие | Очень высокие |
| Независимый деплой | ❌ | ❌ | Частично | Частично | ✅ |
| Скорость старта | ✅ Быстро | Средне | ✅ Быстро | Средне | ❌ Медленно |
| Операционная сложность | ✅ Низкая | ✅ Низкая | ✅ Низкая | Средняя | ❌ Высокая |

## Быстрый ориентир

```
Новый проект, маленькая команда?         → Modular Monolith или Layered
Сложная бизнес-логика, много правил?     → Clean Architecture
Несколько подобластей, большая команда?  → DDD
Независимое масштабирование + большая
организация?                             → Microservices
Простой CRUD?                            → Layered Architecture
Требования неясны?                       → Начни с простого, рефакторь
                                           когда проявятся паттерны.
```

## Clean Architecture

**Основной принцип.** Зависимости направлены внутрь. Внутренние слои не знают о внешних.

```
┌─────────────────────────────────────────────────────────┐
│                    Frameworks & Drivers                  │
│  ┌─────────────────────────────────────────────────┐    │
│  │              Interface Adapters                  │    │
│  │  ┌─────────────────────────────────────────┐    │    │
│  │  │           Application Layer              │    │    │
│  │  │  ┌─────────────────────────────────┐    │    │    │
│  │  │  │         Domain Layer            │    │    │    │
│  │  │  │    (Entities & Business Rules)  │    │    │    │
│  │  │  └─────────────────────────────────┘    │    │    │
│  │  └─────────────────────────────────────────┘    │    │
│  └─────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

**Структура папок (пример на TypeScript):**

```
src/
├── domain/                 # Бизнес-логика (без зависимостей)
│   ├── entities/
│   ├── value-objects/
│   └── repositories/       # Только интерфейсы
├── application/            # Use cases (зависит от domain)
│   ├── use-cases/
│   └── services/
├── infrastructure/         # Внешние зависимости (реализует интерфейсы)
│   ├── database/
│   ├── external/
│   └── config/
└── presentation/           # UI / API слой
    ├── api/
    ├── controllers/
    └── dto/
```

**Правила зависимостей:**

- Domain → ничего (чистая бизнес-логика).
- Application → Domain.
- Infrastructure → Application + Domain (реализует интерфейсы).
- Presentation → Application (вызывает use cases).

**Когда использовать:** сложная бизнес-логика, нужна изоляция от фреймворков, важна тестируемость доменного слоя.

**Когда не использовать:** простой CRUD, малая команда, прототип.

## Domain-Driven Design (DDD)

**Основной принцип.** Структура софта повторяет бизнес-домен. Bounded Contexts задают чёткие границы.

**Стратегические паттерны:**

- Bounded Contexts — явные границы вокруг доменных моделей.
- Context Mapping — как контексты общаются (Shared Kernel, Customer/Supplier, Anti-Corruption Layer).

**Тактические паттерны:**

- Entities — объекты с идентичностью.
- Value Objects — неизменяемые, равенство по значению.
- Aggregates — границы консистентности, инварианты через aggregate root.
- Domain Events — изменения состояния, передаются между контекстами.

**Структура папок (пример на TypeScript):**

```
src/
├── contexts/
│   ├── ordering/
│   │   ├── domain/         # Entities, VOs, events, интерфейсы репозиториев
│   │   ├── application/    # Use cases, command/query handlers
│   │   ├── infrastructure/ # Реализации репозиториев, внешние адаптеры
│   │   └── api/            # HTTP handlers, DTOs
│   ├── inventory/
│   │   └── ...
│   └── shipping/
│       └── ...
└── shared/
    └── kernel/             # Общие базовые классы, интерфейсы
```

**Когда использовать:** богатая бизнес-модель, несколько подобластей с разными правилами, большая команда.

**Когда не использовать:** простой домен, маленькая команда, нет ясных границ между контекстами.

## Microservices

**Когда использовать:**

- Большие команды с независимым деплоем.
- Разные требования к масштабированию у разных сервисов.
- Polyglot persistence.

**Когда не использовать:**

- Маленькая команда (< 10 человек).
- Неясные доменные границы.
- Стартап в поиске product-market fit.

**Паттерны коммуникации:**

- Синхронная (HTTP / gRPC) — запросы, валидация в реальном времени.
- Асинхронная (Events / Messages) — побочные эффекты, eventual consistency.

**Паттерны данных:**

- Database per Service.
- Saga Pattern для распределённых транзакций.

**Цена входа:** операционная сложность, distributed tracing, dev-окружение, тесты интеграции.

## Modular Monolith

**Основной принцип.** Один deployable unit с жёсткими границами модулей. Простая эксплуатация + готовность к будущему извлечению в сервисы.

**Структура папок (пример на TypeScript):**

```
src/
├── modules/
│   ├── users/
│   │   ├── api/           # HTTP handlers
│   │   ├── domain/        # Бизнес-логика
│   │   ├── infra/         # БД, внешние интеграции
│   │   └── index.ts       # Только публичный API
│   ├── orders/
│   │   └── ...
│   └── payments/
│       └── ...
├── shared/                 # Действительно общий код
│   ├── kernel/
│   └── utils/
└── main.ts                # Composition root
```

**Правила коммуникации модулей:**

- Каждый модуль экспортирует публичный API через `index`-файл.
- Другие модули используют ТОЛЬКО публичный API.
- Никаких обращений во внутренности модуля.

**Когда использовать:** средняя сложность, средняя команда, неопределённые требования к масштабированию, желание сохранить простоту деплоя.

**Когда не использовать:** простой CRUD (избыточно) или явная потребность в независимом деплое (тогда сразу микросервисы).

## Layered Architecture

**Основной принцип.** Горизонтальные слои. Каждый слой зависит только от нижележащего.

**Структура папок (пример на TypeScript):**

```
src/
├── routes/                # Presentation (HTTP handlers)
├── controllers/           # Request / response handling
├── services/              # Бизнес-логика
├── models/                # Модели данных
├── repositories/          # Доступ к данным
└── utils/                 # Cross-cutting утилиты
```

**Правила зависимостей:**

- Routes → Controllers → Services → Repositories → Database.
- Запрет на пропуск слоёв (routes не вызывают repositories напрямую).

**Когда использовать:** простой CRUD, маленькая команда, прототип, обучающий проект.

**Когда не использовать:** сложная бизнес-логика (логика расползается по сервисам), множественные подобласти.

## Адаптация примеров

Все структуры папок в этом файле — на TypeScript. При генерации `./workflow/ARCHITECTURE.md` адаптируй под язык проекта:

- **Go** — `internal/`, `cmd/`, `pkg/`, пакетные границы вместо папок-модулей.
- **Python** — пакеты с `__init__.py`, `src/<package>/...`.
- **Rust** — модули с `mod` и `pub use`, `crates/` для multi-crate workspace.
- **Java / Kotlin** — пакеты по доменам, Maven / Gradle модули для жёстких границ.
- **PHP (Laravel)** — `app/Domain/`, `app/Application/`, `app/Infrastructure/`.
- **C# / .NET** — отдельные проекты в solution для каждого слоя.

Идиомы языка важнее буквального копирования папок из примеров.
