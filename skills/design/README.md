# design

## Назначение

`design` описывает UI/UX-решения конкретной фичи. Это единственный владелец `./workflow/features/{slug}/design.md`.

## Ответственность

- Прочитать `feature.md`, `plan.md` и проектный `DESIGN.md`.
- Определить пользовательские сценарии, состояния, layout, компоненты и визуальные ограничения фичи.
- Создать или обновить `./workflow/features/{slug}/design.md`.
- Зафиксировать решения так, чтобы `implement` мог реализовать UI без повторного дизайна.

## Связь с конвейером

`design` работает после `planning`, если фича затрагивает UI. Его результат читают `improve`, `task`, `implement`, `test` и `docs`.

## Почему граница такая

Фичевый дизайн применяет общий `DESIGN.md` к конкретному пользовательскому сценарию. Он не меняет проектный визуальный канон и не пишет код, чтобы не смешивать решение интерфейса с реализацией.

## Входной контекст

- `./workflow/features/{slug}/feature.md`
- `./workflow/features/{slug}/plan.md`
- `./workflow/DESIGN.md`
- существующий frontend-код

## Выходные артефакты

- `./workflow/features/{slug}/design.md`
- служебный хвост в `./workflow/PLAN.md`, если фича упёрлась в отсутствующий проектный дизайн-канон

## Не делает

- Не меняет проектный `DESIGN.md`.
- Не пишет код.
- Не пишет тесты.
- Не переписывает `plan.md`.
- Не делает git-операции.

## Критерий готовности

Фичевый UI описан через конкретные решения, состояния и ограничения, без маркетингового текста и без реализации.
