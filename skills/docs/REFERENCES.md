# REFERENCES — исследование внешних скилов для `docs`

## Метод

Через `find-skills` (`npx skills find`) собраны скилы экосистемы `skills.sh`, близкие по сути к нашему `docs` — создание и обновление пользовательской и технической документации, README, концептуальных и технических страниц. Каждый кандидат разобран на предмет того, что усилит наш скил, не выйдя за его границы (артефакты — корневой `README.md` и `./docs/{concept,spec,tech}/*.md`; скил фиксирует текущее состояние без биографии изменений, не делает аудит, не меняет код, не пишет тесты).

## Принятые усиления

Пять блоков формализуют уже заявленные обязанности скила и дают метод там, где сейчас стоит общая фраза. Все согласованы с принципами (текущее состояние, без биографии и дельт) и не выходят за границы скила.

### A. Различение типов документации (по принципу Diátaxis)

Не смешивать в одном документе объяснение, справку и инструкцию. Использовать различение как опору для назначения трёх существующих папок:
- `./docs/concept/` — объяснение: назначение, идеи, ценность продукта (зачем он);
- `./docs/spec/` — справка: поведение и контракты, к которым обращаются за точным ответом (что делает);
- `./docs/tech/` — устройство и работа с проектом: как он устроен и как с ним работать (как устроено и как запускать).
Полные четыре квадранта Diátaxis поверх трёх папок не вводить.
Источник: `documentation-writer`.

### B. Аудитория и цель документа до написания

Перед написанием каждого документа определить читателя и его задачу: концепт — для понимающего «зачем», spec — для ищущего точный ответ о поведении, tech — для того, кто разворачивает и дорабатывает проект. Содержание подбирается под эту задачу.
Источник: `documentation-writer`, `documentation`, `technical-writing`, `crafting-effective-readmes`.

### C. Чек-лист секций корневого `README.md`

Зафиксировать обязательный состав: имя проекта, краткое описание назначения, быстрый старт / пример использования, конфигурация и запуск. Сейчас скил «поддерживает README» без состава.
Источник: `documentation`, `crafting-effective-readmes`.

### D. Метод обновления существующего документа

При обновлении документации сверять её утверждения с живым кодом, править расхождения и сохранять существующую структуру документа, а не переписывать его заново. Сейчас «обновить документацию на основе фичи» дано без метода.
Источник: `update-oo-component-documentation`.

### E. Самопроверка перед финалом

Перед завершением проверить документ: фактическая точность (код, имена, поведение соответствуют реализации), ясность языка, единая терминология, отсутствие дублирования между документами.
Источник: `documentation-writer`, `technical-writing`.

## Сознательно отклонено

| Что | Источник | Причина |
|---|---|---|
| Changelogs / release notes / version history / отметки breaking changes | `technical-writing`, `update-oo-component-documentation` | Прямой конфликт с принципом «текущее состояние без биографии и дельт» |
| Четыре квадранта Diátaxis как структура папок | `documentation-writer` | Конфликт с существующими тремя папками `concept/spec/tech`; перегруз |
| Фаза «план-аутлайн на одобрение пользователя» | `documentation-writer` | Конвейерный скил работает автономно; интерактивное одобрение не вписывается |
| Детальная API-машинерия (rate limits, пагинация, SDK-примеры) | `documentation` | Слишком специфично, нужно не каждому проекту; контракты API покрывает `spec` без отдельного аппарата |
| Mermaid-диаграммы как обязательный элемент | `technical-writing` | Допустимо лишь опционально, не ядро скила |
| Формальные стандарты C4 / Arc42 / IEEE 1016 | `update-oo-component-documentation` | Тяжёлая формальная машинерия, перегруз |
| Типизация README по виду проекта (OSS / Personal / Internal / Config) | `crafting-effective-readmes` | Избыточно для одного корневого `README.md`; различение аудитории даёт блок B |
