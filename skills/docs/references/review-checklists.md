# Чеклисты ревью документации

## Технический чеклист

Структура, ссылки, полнота:

- [ ] `README.md` ≤ 150 строк (цель ~80–120).
- [ ] README содержит: заголовок, tagline, быстрый старт, пример, таблицу документации, лицензию.
- [ ] Каждый файл `docs/{concept,spec,tech}/*.md` имеет prev/next шапку, упорядоченную по таблице Documentation в README.
- [ ] Первая страница без `[← Предыдущая]`; последняя — без `[Следующая →]`.
- [ ] Каждый файл `docs/{concept,spec,tech}/*.md` имеет секцию `## See Also` с 2–3 ссылками на родственные страницы.
- [ ] Ссылка на README из любой страницы `docs/{category}/*.md` — `../../README.md`.
- [ ] Все внутренние ссылки рабочие (нет битых путей, нет dead-якорей).
- [ ] Код-примеры используют реальные команды и синтаксис проекта.
- [ ] Команды установки реальные — выведены из манифеста пакета.
- [ ] Нет дублирования между README и `./docs/` (кроме команды установки).
- [ ] Нет рассеянных `*.md` в корне, которые должны были попасть в `./docs/tech/`.
- [ ] Папок `concept/`, `spec/`, `tech/` создано столько, сколько использовано; пустых нет.

## Чеклист читабельности — «глазами нового пользователя»

Читай каждую страницу так, будто видишь проект впервые.

### Первые 10 секунд (над фолдом)
- [ ] Понятно за 10 секунд, что делает проект.
- [ ] Tagline конкретный — не маркетинг типа «next-gen решение».
- [ ] Есть реальная команда установки, которую можно скопировать.

### «Показывай, а не рассказывай»
- [ ] В README есть конкретный пример использования, не просто «установи и запусти».
- [ ] Код-блоки показывают реальные команды и реальный вывод, не абстрактные плейсхолдеры.
- [ ] Примеры копируемы — нет `<placeholder>`, который пользователь должен заменить.

### Scannability
- [ ] Любой топик находится за 5 секунд сканированием заголовков.
- [ ] Абзацы короткие (≤ 3–4 строки). Длинные абзацы пропускаются глазом.
- [ ] Списки вместо перечислений через запятую в строку.
- [ ] Таблицы для структурированных данных, а не вложенные буллеты.

### Жаргон и допущения
- [ ] Аббревиатуры раскрыты при первом использовании или есть ссылка на объяснение.
- [ ] Нет допущений о «внутреннем знании»: «как описано в RFC» — в каком RFC?
- [ ] Джуниор-разработчик понимает каждую страницу без расспросов.

### Навигация и поток
- [ ] После README понятно, куда идти дальше.
- [ ] После каждой страницы prev/next и See Also ведут логично.
- [ ] Таблица Documentation в README упорядочена по пути нового пользователя: concept → spec → tech.

### Мотивация
- [ ] README отвечает «зачем мне это?» раньше, чем «как это работает?».
- [ ] Есть «момент wow» — фича или пример, ради которого захочется попробовать.
- [ ] Структура `docs/` не подавляет: суммарно 6–10 страниц на старте.

## Проверка стандартов

Сравни существующую документацию с актуальной структурой. Возможные пробелы:

| Пробел | Как обнаружить | Как починить |
|--------|----------------|--------------|
| Нет prev/next навигации | В шапке только «← Назад к README» без `·`-ссылок на соседей | Добавить prev/next по порядку Documentation table |
| Нет `## See Also` | Файл заканчивается без секции `## See Also` | Добавить с 2–3 ссылками на родственные страницы |
| Плоский `docs/` без подпапок | `docs/*.md` лежит прямо в `docs/`, не в `concept/spec/tech` | Переразложить по трём папкам, обновить ссылки |
| Нет таблицы Documentation в README | README без таблицы со ссылками на `docs/` | Добавить таблицу |
| README слишком длинный | README > 150 строк при наличии `docs/` | Перенести избыток в соответствующие страницы `docs/` |

Найденные пробелы фиксируй в audit-отчёте наравне с контентными проблемами. Молча не правь существующие файлы — покажи план, дождись подтверждения пользователя.

```
  ✅ Ссылки проверены (14 внутренних, 0 битых)
  ✅ README — 108 строк
  ✅ Все страницы имеют навигацию
  ⚠️  docs/tech/api.md содержит плейсхолдер вместо реального эндпоинта

Читабельность:
  ✅ README объясняет назначение за первые 10 секунд
  ✅ Все код-примеры копируемы
  ⚠️  docs/tech/architecture.md содержит абзац на 12 строк — разбит на 3
  ⚠️  «CQRS» использовано без расшифровки в docs/tech/architecture.md

Применённые правки:
  → Длинный абзац в docs/tech/architecture.md разбит на 3 коротких
  → После первого упоминания CQRS добавлено «(Command Query Responsibility Segregation)»
  → Плейсхолдер в docs/tech/api.md заменён реальным эндпоинтом

Все проверки пройдены ✅
```
