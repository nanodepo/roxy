# feature

## Назначение

`feature` превращает сырую просьбу пользователя в самодостаточный feature brief. Скил отвечает за первичный разбор фичи: что пользователь просит, какую проблему это закрывает, какие термины и границы уже понятны, а что остаётся вопросом для следующих этапов.

## Ответственность

- Разобрать запрос пользователя: тип работы, ключевую функциональность, доменные термины и ожидаемый результат.
- Определить, запрос описывает проблему, решение, улучшение, исправление или рефакторинг.
- Поднять только проектный контекст, который нужен для понимания смысла фичи.
- Проверить активные фичи, чтобы не создать дубль.
- Задать короткие уточняющие вопросы, если без них feature brief будет двусмысленным.
- Создать slug фичи в стабильном формате.
- Создать директорию `./workflow/features/{slug}/`.
- Создать `feature.md` как самодостаточный brief.
- Зафиксировать суть, проблему или потребность, пользователя или контекст, ожидаемый результат, границы, не-цели и открытые вопросы.
- Добавить в `./workflow/PLAN.md` служебную строку фичи со статусом `[ ]`.

## Связь с конвейером

`feature` открывает фичевую ветку workflow. После него `planning` превращает brief в план. `design`, `test` и `docs` могут читать `feature.md`, но `feature` не проектирует для них отдельные артефакты.

## Почему граница такая

Feature brief должен быть богаче одной фразы, но беднее PRD и плана. Он фиксирует смысл, проблему, границы и намерение, не принимая решений о реализации, дизайне, тестах или документации. Строка в `PLAN.md` только делает фичу видимой для конвейера.

## Входной контекст

- запрос пользователя
- `./workflow/PROJECT.md`
- `./workflow/VISION.md`
- `./workflow/ROADMAP.md`
- `./workflow/DESIGN.md`, если фича явно затрагивает UI
- существующий `./workflow/PLAN.md`

## Выходные артефакты

- `./workflow/features/{slug}/feature.md`
- служебная строка фичи в `./workflow/PLAN.md`

## Не делает

- Не пишет `plan.md`.
- Не пишет `design.md`.
- Не пишет `tests.md`.
- Не пишет задачи `NN-task.md`.
- Не пишет код.
- Не пишет PRD.
- Не пишет acceptance criteria как тестовый план.
- Не создаёт ветки, worktree и другие git-артефакты.
- Не вызывает следующие скилы автоматически.
- Не делает git-операции.

## Критерий готовности

Фича описана так, чтобы следующий агент мог спланировать её без знания истории разговора: понятны суть запроса, проблема или потребность, пользовательский контекст, ожидаемый результат, границы, не-цели и открытые вопросы.
