# Forge — фабрика кастомных скилов из других скилов

## Назначение

Берёт скил из `~/.agents/skills/*`, накладывает правила рабочего процесса, пишет в `.claude/skills/{name}/SKILL.md` относительно cwd.

Forge — мета-скил. Не пишет код. Собирает скилы.

Самодостаточен. Анализ, опрос, draft, сжатие — внутри. Единственный внешний вызов — `mcp__sequential-thinking__sequentialthinking` на аналитических этапах.

## Параметры

Строка `args`:

```
<skill-path> <new-skill-name>
```

- `skill-path` — абсолютный путь к папке исходного скила (обычно `~/.agents/skills/<...>`).
- `new-skill-name` — slug (латиница, дефисы, без пробелов). Имя папки + значение `name` во frontmatter.

Меньше двух токенов или путь не существует → остановись, объясни формат, подскажи пути из `~/.agents/skills/*`.

## Жёсткие правила (все этапы)

1. **`mcp__sequential-thinking__sequentialthinking`** на этапах 4, 6, 8. Не опция.
2. **Никаких git.** Не `git status`, `git diff`, `git add`, `git commit`, `git branch`, `git checkout`. Не делай ветки, не предлагай коммиты. Грязное дерево — норма. Пользователь сам решает.
3. **Язык пользователя** в теле SKILL.md и коммуникации. Имена скилов, флаги, ключи frontmatter, идентификаторы команд — в оригинале.
4. **Жёсткий контракт через режим планирования.** На этапе 1 заведи в режиме планирования агента (todo-список / план задач — что доступно в текущем агенте) ровно 10 пунктов, по одному на этап. После **каждого** `mcp__sequential-thinking__sequentialthinking` и каждого `AskUserQuestion` твоё **следующее** действие — закрыть пункт текущего этапа и явно прочитать пункт следующего, до любых других действий и текстового ответа. Завершение вложенного вызова = закрытие одного из 10 пунктов, не финал forge. Сессия не завершается, пока есть открытые пункты.
5. **Материализация артефактов.** Любой существенный промежуточный результат (ответы этапа 5, draft этапа 6, сжатые версии этапа 7) **сразу** пишется через `Write` в `.claude/skills/{new-skill-name}/.forge-tmp/...` (см. этапы 5–7). **Не** ответ пользователю и **не** финал — промежуточный файл. Следующий этап **начинается** с `Read` этого файла, не «по памяти». `.forge-tmp/` удаляется в конце этапа 9.
6. **Никаких упрощений.** Все этапы (sequential-thinking → опрос → draft → сжатие → запись) строго в порядке.
7. **References исходника.** Папка `references/` — часть инструкций, не декор. Читается полностью (этап 2), анализируется (этап 4), материал для draft (этап 6), сжимается отдельно (этап 7), пишется в `.claude/skills/{new-skill-name}/references/` (этап 9). На каждом шаге проверяй соответствие требованиям — что не подходит, переписывай или выбрасывай, не копируй слепо.
8. **Законы Маркова.** Перед этапом 4 прочитай `.claude/skills/forge/references/markov-laws.md` — свод принципов агентной работы (достаточное настоящее, без биографии, инвариант не эпизод, и т.д.). Законы **не копируются** в новый скил отдельным файлом и не приводятся списком. Forge выбирает применимые и формулирует как **естественные требования внутри инструкций** нового SKILL.md — без упоминания «закон такой-то», без номеров. Цель — новый скил работает по принципам, не зная имени «законы Маркова».

## Этапы

### 1. Распарсить `args` и зафиксировать план

Разбей строку по пробелам. Ожидается 2 токена. Не так → сообщи формат, остановись.

После парсинга — 10 пунктов в режиме планирования агента:

1. Распарсить `args` и зафиксировать план
2. Прочитать исходный скил
3. Проверить целевую папку
4. Анализ и план нового скила (sequential-thinking)
5. Уточняющие вопросы пользователю (условно)
6. Сгенерировать draft SKILL.md и references
7. Сжать draft и references
8. Финальная сверка (sequential-thinking)
9. Записать финальные файлы
10. Отчёт

Без этого дальше не идёшь. Закрой пункт 1 → пункт 2.

### 2. Прочитать исходный скил

- `Read` по `{skill-path}/SKILL.md` — главный документ.
- `Bash ls {skill-path}` — что ещё рядом.
- **`references/`** — есть → прочитай **все** файлы. Часть инструкций скила, даже если в `SKILL.md` не упомянуты явно. Список + краткое содержимое каждого файла — фиксируй для этапа 4.
- `agents/`, `scripts/`, `assets/` и прочее — читай только упомянутое в `SKILL.md` или `references/*`. Полный контекст работы исходника, без лишнего.

Основной `SKILL.md` не существует → остановись, сообщи пользователю, предложи пути из `~/.agents/skills/`.

Закрой пункт 2 → пункт 3.

### 3. Проверить целевую папку

`Bash test -d .claude/skills/{new-skill-name}`. Существует → спроси через `AskUserQuestion`: перезаписать или прервать. Никаких автоматических перезаписей.

Папка создаётся лениво через `mkdir -p` — впервые на этапах 5/6/7 (для `.forge-tmp/`), окончательное наполнение — этап 9. Закрой пункт 3 → пункт 4.

### 4. Анализ и план нового скила (sequential-thinking)

Прочитай `.claude/skills/forge/references/markov-laws.md` (если не читал).

Через `mcp__sequential-thinking__sequentialthinking` ответь:

- Тип скила? Выбери из категорий ниже («Спец-указания по типам»). Ни одна не подходит → общий случай.
- Что сохраняем буквально / переписываем / выбрасываем?
- Какие требования к создаваемым скилам применимы?
- Какие файлы в `./workflow/...` читать / создавать / обновлять?
- Какие вопросы скил задаст пользователю при запуске (на этапе работы скила, не forge)?
- Какие открытые вопросы у тебя — для этапа 5.
- **По каждому файлу `references/`:** сохранить / переписать (что менять) / объединить / выбросить. Ценный, но требует адаптации → отметь, опиши что менять.
- **Какие законы Маркова применимы?** Не все — только реально влияющие (документирование → «без биографии», «канонического состояния», «переписывания, а не дописывания»; тестирование → «инвариант, не эпизод»; планирование и таск-разбивка → «бюджет внимания», «чистая передача»). Для каждого зафиксируй **где** в новом SKILL.md его принцип отразить (этап такой-то, формулировка такая-то). Материал для этапа 6 — там законы растворяются в тексте, без имён.
- **Какой уровень правил сжатия встраивать?** По матрице «Сжатие финальных артефактов — инлайнится в создаваемые скилы»: полный / краткий / нет. Матрица не покрывает тип явно → исходи из объёма выходного артефакта: длинный текстовый документ → полный; короткий текстовый артефакт → краткий; код → нет. Зафиксируй решение + **имена артефактов**, к которым правила применяются.

Зафиксируй итог как структурированный план (в собственном контексте, без временных файлов). Закрой пункт 4 → пункт 5.

### 5. Уточняющие вопросы пользователю (условно)

**Принципы:**

- **Сначала попробуй ответить из материалов.** Ответ выводится из:
  - исходного `SKILL.md` + `references/` (прочитаны на этапе 2),
  - проекта (`./workflow/VISION.md`, `./workflow/GOALS.md`, `./workflow/PROJECT.md`, `./workflow/ARCHITECTURE.md` — `Read` по необходимости),
  - кода, релевантного скилу (тестирование → `Bash ls` тестовых папок),
  
  → ответ из материала, вопрос не задаётся.

- **Закрытый список вопросов.** Только нерешённые вопросы этапа 4. Этап 4 без вопросов → этап 5 пропускается.

- **По одному связанному блоку.** Группируй зависимые через `AskUserQuestion` (1–4 независимых в одном блоке). Зависимые — последовательно: ранний ответ влияет на формулировку позднего.

- **Рекомендованный ответ для каждого вопроса.** В `AskUserQuestion` каждый вариант: первый — «(Recommended)» + явное мнение forge почему. Снижает нагрузку, ускоряет опрос. Пользователь может выбрать «Other» с произвольным ответом.

- **Каждый вопрос про создаваемый скил, не про forge.** Опрос уточняет работу нового скила: какие артефакты, проверки, вопросник пользователю при запуске.

**Процедура:**

1. Список нерешённых вопросов этапа 4.
2. Каждый — попытка ответить из материалов. Получилось → фиксируй как «найдено из {источник}».
3. Оставшиеся группируй и задавай через `AskUserQuestion`. Для каждого — рекомендованный вариант первым с «(Recommended)».
4. Собирай ответы. Новая неоднозначность из ответа → добавь в список, продолжай. Нет новых неясностей → опрос закончен.
5. **Сразу после закрытия опроса**, до любых других действий:
   - `Bash mkdir -p .claude/skills/{new-skill-name}/.forge-tmp`.
   - `Write .claude/skills/{new-skill-name}/.forge-tmp/05-grill-answers.md` — все ответы (материалы + пользователь) с привязкой к исходным вопросам этапа 4 + обновлённый план.
   - Закрой пункт 5 → пункт 6.

Этап 4 без вопросов → этап 5 пропускается без файла, пункт 5 закрывается.

### 6. Сгенерировать draft SKILL.md и references

Запусти `mcp__sequential-thinking__sequentialthinking` для draft — аналитический этап, forge решает как структурировать инструкции.

**Входные данные:**

- финальный план этапа 4 + поправки этапа 5;
- `Read .claude/skills/{new-skill-name}/.forge-tmp/05-grill-answers.md` (если есть);
- обязательные требования (см. «Требования к создаваемым скилам»);
- структура `./workflow/...`;
- ограничения: язык пользователя, запрет git;
- исходный `references/*` + решения этапа 4 (сохранить / переписать / объединить / выбросить);
- выбранные принципы законов Маркова — пары «куда вписать → какую установку сформулировать». Установка пишется как обычное требование («артефакты описывают текущее состояние, без истории», «имена тестов — про инвариант, не про инцидент», «после имплементации временные заметки удаляются»), без упоминания «закона», номера, источника;
- решение этапа 4 по сжатию: какой уровень встраивать (полный / краткий / нет; матрица). Полный или краткий → в SKILL.md секция «## Сжатие финального артефакта» с правилами, адаптированными под язык + имена артефактов, + на нужном этапе явный шаг «применить правила секции "Сжатие финального артефакта" к {имя-файла} перед записью». Нет → никаких упоминаний сжатия.

**Правила написания SKILL.md:**

#### Frontmatter

```yaml
---
name: {new-skill-name}
description: >
  {краткое «что делает»} + явные триггеры (фразы пользователя, типы задач).
  «Используй когда {конкретные контексты}» — формулировка достаточно «толкающая»,
  чтобы агент не пропустил скил там, где он уместен.
---
```

Description — главный механизм триггеринга. Включай:
- что скил делает (1–2 предложения);
- явные триггер-фразы пользователя в кавычках или маркерах («создай фичу», «начать фичу», `/feature`, «add feature»);
- контексты применения, даже без имени скила («когда пользователь говорит о добавлении новой функциональности и хочет зафиксировать как фичу»).

Description не маркетинг, но не сухой — преодолевает дефолтный «undertriggering».

#### Тело SKILL.md

Структура секций (порядок):

```markdown
# {Название скила}

## Назначение
Что делает, на что опирается, что не делает.

## Параметры
Параметры есть → формат, обязательные/необязательные, что при отсутствии.
Параметров нет → секция пропускается.

## Жёсткие правила
Инварианты на всех этапах. Запрет git, язык пользователя,
обязательный sequential-thinking (если применимо), обязательный caveman ultra
(если применимо), материализация артефактов, обновление PLAN.md.

## Этапы
Нумерованные шаги. Императив («прочитай», «запиши», «спроси»).
Каждый этап: что читать, что писать, какие инструменты звать.

## Требования к артефактам
Какие файлы создаёт, по какой структуре, в каком формате.

## Обновление PLAN.md
Что и в какой раздел фиксируется в `./workflow/PLAN.md` в финале.

## Замечания
Особые случаи, известные ограничения, что при отсутствии файлов.
```

Не каждая секция обязательна — пропускай неприменимые.

#### Стиль письма

- **Императив**: «прочитай X», «запиши Y», «спроси Z». Не «следует прочитать», не «можно записать».
- **«Почему»** там, где не очевидно. Не «MUST», а «потому что …». Заглавные «MUST»/«NEVER» — только когда нарушение ломает работу (запрет git, обязательный sequential-thinking).
- **Theory of mind**: пиши так, словно агент-исполнитель без контекста создания скила. Видит только настоящее: SKILL.md, references, файлы проекта. Нужна предыстория → настоящее недоопределено; фиксируй недостающее как явную инструкцию.
- **Без биографии**: SKILL.md описывает работу **сейчас**. Не «раньше делали X, теперь Y», не «после рефакторинга». Только текущее состояние.
- **Без дельта-инструкций**: правило снято → его нет в SKILL.md. Никаких «раньше запрещено, теперь можно».
- **Конкретные имена**: пути, MCP, инструменты, файлы — полным именем (`mcp__sequential-thinking__sequentialthinking`, `./workflow/PLAN.md`, `./workflow/features/{slug}/feature.md`). Не «seq-thinking», не «план» вместо `./workflow/PLAN.md`.

#### Анатомия папки

```
.claude/skills/{new-skill-name}/
├── SKILL.md (обязателен)
│   ├── YAML frontmatter (name, description)
│   └── Тело на языке пользователя
└── references/ (опционально)
    └── *.md — материалы, подгружаемые по необходимости из этапов SKILL.md
```

`scripts/` и `assets/` forge **не создаёт по умолчанию**. Есть в исходнике + решение этапа 4 «сохранить» → копируются 1:1, без переписываний.

#### References нового скила

По решению этапа 4:

- **сохранить как есть** — копия 1:1 в финальную папку (с сохранением имени), без сжатия этапа 7;
- **переписать** — новый текст с поправками этапа 4;
- **объединить** — два+ файла в один; имя — самое осмысленное из исходных;
- **выбросить** — нет в финальной папке.

Главный SKILL.md ссылается на references по имени, объясняя **в каком этапе** читать и **зачем**.

#### Что НЕ должно попасть в новый SKILL.md

- Ссылки на `.claude/skills/forge/references/markov-laws.md`, «законы Маркова», номера законов.
- Упоминания forge (новый скил не должен знать, что его собрал forge).
- Истории про прошлые версии скила.
- Тесты в скилах, где не их задача (см. спец-указания).
- Git-операции в любой форме.

**Процедура:**

1. По плану этапа 4 + ответам этапа 5 составь черновик SKILL.md как единый markdown.
2. По решениям этапа 4 для каждого `references/`: черновик (для «переписать» / «объединить») или отметка «сохранить как есть» / «выбросить».
3. **Сразу после готовности черновиков**, до любых действий:
   - `Bash mkdir -p .claude/skills/{new-skill-name}/.forge-tmp` (если не создана).
   - `Write .claude/skills/{new-skill-name}/.forge-tmp/06-draft-skill.md` — черновик SKILL.md.
   - Каждый черновик references: `Write .claude/skills/{new-skill-name}/.forge-tmp/06-draft-ref-{filename}` (имя = финальное).
   - Каждый «сохранить как есть»: `Bash cp {source-path} .claude/skills/{new-skill-name}/.forge-tmp/06-keep-ref-{filename}` — отметка «не сжимать этапом 7, только перенести этапом 9».
   - Закрой пункт 6 → пункт 7.

Не работай с черновиками «в памяти» — следующий этап читает их с диска.

### 7. Сжать draft и references

**По одному черновику за раз**, циклом по `.claude/skills/{new-skill-name}/.forge-tmp/06-draft-*`:

1. `Read` исходного черновика.
2. Применить правила сжатия ниже.
3. `Write .claude/skills/{new-skill-name}/.forge-tmp/07-compressed-{что-то}.md` со сжатым результатом (имя файла повторяет суффикс исходного: `skill.md` для SKILL, имя референса — для референсов).
4. Следующий черновик.

Файлы `06-keep-ref-*` («сохранить как есть») **не сжимаются** — переедут в финальную папку без изменений на этапе 9.

Все `06-draft-*` обработаны + для каждого есть `07-compressed-*` → закрой пункт 7 → пункт 8.

**Правила сжатия (ultra):**

#### Что сохраняется без изменений

- **frontmatter** — целиком, символ в символ.
- **Имена** скилов, MCP, инструментов, файлов, путей, переменных, ключей frontmatter, команд, env-переменных.
- **Код-блоки** (```bash, ```yaml, ```json, ```markdown и т.д.) — содержимое не трогается.
- **Имена методов, функций, API, типов, классов, констант** — полным именем.
- **Сообщения об ошибках** в кавычках или код-форматировании.
- **Структура** `./workflow/...` (имена файлов и папок).
- **Внутренние заголовки** `references/*` и `SKILL.md`, если существенны для навигации.
- **Числа, версии, ID, хеши, временные метки.**

#### Что убирается

- **Филлер**: «как правило», «в общем», «в принципе», «по сути», «в действительности», «практически», «именно», «прямо», «фактически», «непосредственно», «собственно».
- **Вежливость**: «пожалуйста», «было бы здорово», «давайте», «попробуем», «можешь сделать», «не мог бы ты».
- **Хеджирование**: «возможно», «может быть», «вероятно», «как-то так», «по идее», «скорее всего», «в целом».
- **Лишние обороты**: «дело в том, что», «стоит отметить, что», «важно понимать, что» → прямое утверждение.
- **Дублирование** одной мысли в соседних предложениях — оставляй одно.

#### Замена короткими синонимами

Короткий синоним сохраняет смысл → заменяй:

- «осуществить» → «сделать»
- «реализовать решение для» → «решить»
- «произвести анализ» → «проанализировать»
- «выполнить запись» → «записать»
- «является» → опустить или тире
- «представляет собой» → «—» или «это»
- «должен быть выполнен» → «выполняется» или «делай»

Не правило о замене **всех** оборотов — только где не теряется нюанс. Технические термины не заменяются.

#### Ultra-приёмы

- **Стрелки для причинности**: «X приводит к Y» → «X → Y»; «Y вытекает из X» → «X → Y».
- **Один токен вместо двух**, если смысл сохраняется и нет двусмысленности.
- **Сокращения общеизвестного** — **только** если встречаются в исходном русскоязычном контексте проекта («БД», «конфиг», «UI»). **Не изобретай** новых; не вводи английские аббревиатуры в русский текст без оснований.
- **Фрагменты-перечисления** вместо полных предложений в списках, где каждое утверждение атомарно («`Read` файл X. `Write` файл Y.»).

#### Где НЕ применять сжатие

Полные предложения, без жертв ради токенов:

- Шаги, где порядок критичен и фрагментация может его сломать.
- Условные «если X — делай Y, иначе Z».
- Описания ветвлений, зависимостей, побочных эффектов.
- Предупреждения об опасных или необратимых операциях.
- Места, где сжатие создаёт двусмысленность.
- Подписи к параметрам frontmatter (description обычно остаётся читаемым на естественном языке).

#### Принцип

Смысл и операционность важнее краткости. Сжатие даёт ~50–60% reduction в нарративных секциях, ~10–20% в процедурных. Не жми там, где вредно — оставляй полное предложение.

#### Что точно НЕ делается

- Не переводить слова на английский ради краткости.
- Не выкидывать обязательные этапы из инструкций целевого скила.
- Не сжимать примеры кода и команд.
- Не сокращать имена файлов и пути.

### 8. Финальная сверка (sequential-thinking)

Сначала `Read` каждого `.claude/skills/{new-skill-name}/.forge-tmp/07-compressed-*.md` — сверка по диску, не «по памяти».

Через `mcp__sequential-thinking__sequentialthinking` пройди по чеклисту ниже. Сжатый результат удовлетворяет каждому применимому пункту. Потеряно при сжатии → восстанови точечно через `Edit` соответствующего `07-compressed-*.md`, без расжатия всего файла.

**Чеклист (по сжатым файлам):**

- frontmatter сохранён, `name` = `{new-skill-name}`, description содержит явные триггеры;
- все инструменты названы полным именем (`mcp__...`, `Skill('...')`);
- структура `./workflow/...` упомянута где скил с ней работает;
- обязательный sequential-thinking прописан, если тип скила требует;
- матрица сжатия требует полный/краткий → секция «## Сжатие финального артефакта» присутствует с нужным объёмом правил + явный шаг применения к имени конкретного артефакта на нужном этапе;
- матрица требует «не применяется» → нет упоминаний сжатия, нет вызовов `Skill('caveman', ...)`, нет ссылок на caveman;

- язык — пользовательский, имена в оригинале;
- запрет git-операций присутствует;
- никаких упоминаний forge, законов Маркова, файлов forge, имени «caveman» в новом SKILL.md.

Отдельно — интеграция принципов законов Маркова:

## Требования к создаваемым скилам

Каждый создаваемый forge скил соответствует пунктам ниже. Этап 6 — перечисли применимые при составлении черновика, этап 8 — проверь наличие.

### Универсальные (для всех)

- `frontmatter` с `name` и `description`. Описание: короткое «что делает» + явные триггеры (фразы пользователя) + достаточно «толкающая» формулировка «используй когда …» против undertriggering.
- Тело — язык пользователя.
- Запрет на git-операции в любом виде (не проверять статус, не коммиты/ветки/push).
- Скил следует инструкциям буквально, без сокращений «по ситуации».
- Применимые принципы из `.claude/skills/forge/references/markov-laws.md` встроены как естественные требования. Сами законы, номера, имя свода в тексте нового скила не упоминаются.

### Sequential-thinking — обязателен для категорий

- создание фичи (`feature`),
- планирование (`planning`),
- разбивка плана на задачи (`task`),
- улучшение плана (`improve`),
- анализ кода/документации,
- документирование (`docs`).

Скил явно инструктирует вызов `mcp__sequential-thinking__sequentialthinking` на этапах размышления.

### Сжатие финальных артефактов

Правила сжатия встраиваются в SKILL.md создаваемого скила, отдельной секцией «Сжатие финального артефакта» (язык пользователя). Внешних вызовов сжатия внутри нового скила нет — он работает без зависимости от других скилов в окружении. Объём и детальность правил — под тип скила и размер выходного артефакта.

**Матрица применимости (решение принимается на этапе 4):**

| Тип скила | Артефакт | Уровень сжатия |
|-----------|----------|----------------|
| `planning` | `plan.md`, `tests.md` | полный набор правил |
| `improve` | `plan.md`, `tests.md` | полный набор правил |
| `task` | `plan.md` (переписанный), `NN-task.md` | полный набор правил |
| `docs` | `docs/concept/*`, `docs/spec/*`, `docs/tech/*` | полный набор правил |
| `feature` | `feature.md` | краткий набор правил |
| `initialize` | `VISION.md`, `GOALS.md`, `PROJECT.md` | краткий набор правил |
| `implement` | код в репозитории | сжатие не применяется |
| `test` | код тестов | сжатие не применяется |

**Полный набор правил** — то же, что этап 7 forge: что сохраняется (frontmatter, имена, код, структура `./workflow/`, числа, ошибки), что убирается (филлер, вежливость, хеджирование, лишние обороты, дублирование), замена короткими синонимами, ultra-приёмы (стрелки причинности, короткие фрагменты в перечислениях, общеизвестные сокращения **только из исходного контекста**), где НЕ применять (условные ветвления, предупреждения об опасных операциях, неоднозначные места, description во frontmatter). Скилы с объёмным текстовым выходом.

**Краткий набор правил** — базовое: убрать филлер, вежливость, хеджирование, лишние обороты; сохранить имена/код/пути/числа; не сжимать предупреждения и условные конструкции. Без ultra-приёмов и без замены синонимами — артефакты короткие, агрессивное сжатие даст мало и рискует двусмысленностью.

**Сжатие не применяется** — основной артефакт это код. Текстовые заметки в коде (комментарии, docstrings) — стандартный стиль, отдельной секции в SKILL.md не нужно. Скил пишет короткий текстовый отчёт пользователю → правила берутся из контекста на лету; в SKILL.md не закрепляются.

**Что встраивает forge этапом 6:**

- Полный набор → секция «## Сжатие финального артефакта» в SKILL.md с подразделами «Что сохраняется», «Что убирается», «Замена короткими синонимами», «Где НЕ применять». Адаптация этапа 7 forge под язык + имена артефактов скила.
- Краткий набор → короткая секция «## Сжатие финального артефакта» с 3–4 буллетами: «убрать филлер X», «сохранить Y», «не сжимать Z».
- В обоих случаях в SKILL.md есть **явный шаг** на нужном этапе работы: «применить правила секции "Сжатие финального артефакта" к {имя-файла} перед его записью».

**Имя «caveman» в созданном SKILL.md не упоминается.** Просто инструкция по сжатию текста перед записью в файл. Источник правил + имя свода в новом скиле не фигурируют — как и с законами Маркова.

### Режим планирования задач — рекомендация (не запрет)

Для создаваемых скилов **не вводи запрет** на встроенный режим планирования агента. Вместо запрета — **рекомендуй**, если процедура длинная или с вложенными вызовами скилов:

- создание фичи (`feature`),
- планирование (`planning`),
- разбивка плана на задачи (`task`),
- улучшение плана (`improve`),
- реализация фичи (`implement`),
- документирование (`docs`),
- инициализация контекста (`initialize`-подобные).

Атомарные или 1–2-шаговые скилы → **не упоминай** режим планирования вовсе. Не запрещай явно. Молчание лучше избыточной инструкции.

Формулировка рекомендации — нейтральная по агенту: «встроенный режим планирования задач (todo-список / план задач — что доступно в текущем агенте)». Не привязывай к именам инструментов (`TaskCreate`, `update_plan` и т.п.) — различаются между агентами.

### Структура артефактов (обязательна)

```
./workflow/
├── PLAN.md                 # общий статус фич + «хвосты» для дальнейшего разбора
├── VISION.md               # идеологическое видение проекта
├── GOALS.md                # цели разработки
├── ARCHITECTURE.md         # архитектура проекта
├── PROJECT.md              # тех-стек, запуск, деплой и всё, что нужно агенту для работы
├── archive/                # закрытые фичи
└── features/
    └── {slug}/
        ├── feature.md      # описание фичи (поверхностное)
        ├── plan.md         # план реализации с чекбоксами задач и ссылками
        ├── design.md       # дизайн фичи (если применимо)
        ├── tests.md        # описание тестов (только базовая бизнес-логика)
        └── NN-task.md      # задачи после разбивки плана (01-task.md, 02-task.md, ...)
```

Каждый скил создаёт только свои файлы. Никаких объединённых артефактов.

### Обновление `PLAN.md`

Каждый создаваемый скил в финале обновляет `./workflow/PLAN.md`:

- зафиксировать статус фичи (`[ ]` Новая фича | `[-]` Прошла планирование/уточнение | `[+]` Разбита на задачи | `[x]` Выполнена | `[*]` Покрыта тестами и протестирована | `[/]` Перенесена в архив);
- найденные «хвосты», которых скил не вправе касаться → раздел хвостов для пользователя.

### Спец-указания по типам

- **initialize** — добавь к стандартной инициализации опрос пользователя для `VISION.md`, `GOALS.md`, `PROJECT.md`. Вопросы — заранее в скиле. Уровень проекта меняет подход к фичам → этап нельзя пропускать. **`ARCHITECTURE.md` initialize не создаёт** — отдельный скил, анализ архитектуры может требовать большого и дорогого по контексту разбора. `initialize` оставляет в `PLAN.md` хвост-напоминание, что архитектура не зафиксирована.
- **feature** — поверхностно, без use case / user story / описания тестов / методов проверки. Максимум — ожидаемый результат. Анализ незакрытых вопросов, сверка с `VISION.md`/`GOALS.md`/`PROJECT.md`.
- **planning** — глубокий разбор кода и фичи; подробный, без раздувания. Отдельный файл — `tests.md`: только базовая бизнес-логика, поведение, доступность страниц, наличие нужной информации. Чем меньше тестов, тем лучше. Сложные сценарии — только если фича действительно сложная.
- **task** — создаёт `NN-task.md` для каждой задачи. Таск самодостаточен по контексту, не дублирует `feature.md` и `plan.md`. План **переписывается**: чекбоксы `[ ]`/`[x]` + ссылки на таски, без лишнего контекста, раздувшего бы каждый таск.
- **improve** — те же правила, что `planning`.
- **implement** — реализация по таску. Никаких тестов в этом скиле.
- **docs** — документация в `./docs/{concept,spec,tech}/`. Три вида: концептуальная (что и зачем), спецификация (требования и user story), техническая (как устроено). Никаких тестов. Чистота: не описывать регрессии, не косметику («передвинули кнопку»), не оставлять следов прошлых итераций.
- **test** — тесты только по `tests.md` или фиче. Базовые проверки. Не покрывать очевидное. Не писать тесты «что-то удалено».
