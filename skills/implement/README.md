# implement

## Назначение

`implement` пишет продуктовый код фичи и отмечает выполненные пункты плана. Скил отвечает за реализацию, а не за планирование, дизайн, тестирование или документацию.

## Ответственность

- Реализовать одну задачу, одну фазу или простую фичу напрямую по `feature.md`.
- Читать `plan.md`, `NN-task.md` и `design.md`, если они есть.
- Менять код проекта в рамках задачи.
- Переключать выполненные чекбоксы в `plan.md`.
- Обновить служебный статус фичи в `./workflow/PLAN.md` на `[x]`, когда вся фича реализована.

## Связь с конвейером

`implement` обычно работает после `task`, но может работать по `plan.md` или напрямую по `feature.md` для простой фичи. После него идут `test` и `docs`.

## Почему граница такая

Реализация должна быть сосредоточена на продуктовом коде и фактическом прогрессе. Планирование, тестовый канон и документация отделены; статус в `PLAN.md` только отражает завершение реализации.

## Входной контекст

- `./workflow/features/{slug}/feature.md`
- `./workflow/features/{slug}/plan.md`, если есть
- `./workflow/features/{slug}/NN-task.md`, если есть
- `./workflow/features/{slug}/design.md`, если есть
- проектные workflow-документы
- кодовая база проекта

## Выходные артефакты

- изменения в продуктовом коде проекта
- обновлённые чекбоксы в `plan.md`
- обновлённый служебный статус в `./workflow/PLAN.md`

## Не делает

- Не создаёт новый план для сложной фичи вместо `planning`.
- Не пишет `tests.md`.
- Не пишет тестовый код.
- Не пишет документацию.
- Не делает git-операции.

## Критерий готовности

Код реализует заявленный скоуп, план отражает фактический прогресс, а незавершённые вопросы вынесены пользователю или в хвосты.
