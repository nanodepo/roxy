# REFERENCES.md

## Назначение

Этот материал помогает усилить `implement` без расширения его ответственности. Скил остается этапом реализации: он пишет продуктовый код в рамках выбранной задачи, фазы или простой фичи, обновляет фактический прогресс в `plan.md` и служебный статус в `./workflow/PLAN.md`, но не создает план, тестовый канон, тестовый код, документацию, ветки или коммиты.

## Близкие скилы и полезные идеи

### `addyosmani/agent-skills@incremental-implementation`

Источник: https://eliteai.tools/agent-skills/incremental-implementation

Суть: реализация через небольшие проверяемые инкременты.

Что взять:

- Выполняй работу тонкими вертикальными срезами: один законченный кусок поведения, затем проверка, затем следующий кусок.
- Не писать большой объем кода до первой проверки.
- Каждый инкремент должен оставлять проект в рабочем или явно диагностированном состоянии.
- При сложной задаче выбирай порядок по зависимостям, а не по видимой важности.

Что не брать:

- Обязательные коммиты после каждого инкремента.
- Обязанность писать тесты внутри `implement`. Если для проверки нужен тестовый код, это хвост для `test`.

### `addyosmani/agent-skills@context-engineering`

Источник: https://github.com/addyosmani/agent-skills/blob/main/skills/context-engineering/SKILL.md

Суть: загружать ровно тот контекст, который нужен для текущей правки.

Что взять:

- Перед правкой прочитай релевантные workflow-документы и файлы, которые будешь менять.
- Найди локальный пример похожего паттерна в кодовой базе и следуй ему.
- Прочитай связанные типы, интерфейсы, конфиги и соседние модули, если они влияют на изменение.
- При конфликте между планом и кодовой базой явно остановись и вынеси противоречие пользователю.

Что не брать:

- Создание отдельного rules-файла как обязанность `implement`.
- Большие context packs. Скил должен поднимать только контекст текущей задачи.

### `addyosmani/agent-skills@spec-driven-development`

Источник: https://github.com/addyosmani/agent-skills/blob/main/skills/spec-driven-development/SKILL.md

Суть: не писать код без понятных требований, критериев готовности и границ.

Что взять:

- Перед реализацией проверь, что есть достаточный скоуп: `NN-task.md`, `plan.md` или простая `feature.md`.
- Если скоуп размытый, не придумывай требования внутри `implement`; передай работу в `planning` или задай короткий вопрос.
- Задача должна иметь понятное "готово": какое поведение появляется, какие файлы затрагиваются, как проверить результат.
- Если во время реализации меняется решение, синхронизируй это с артефактом фичи, а не оставляй знание только в чате.

Что не брать:

- Полный spec-first workflow. В этом конвейере его выполняют `feature`, `planning`, `improve` и `task`.
- Human review gates между всеми фазами как обязательный механизм.

### `addyosmani/agent-skills@source-driven-development`

Источник: https://explainx.ai/skills/OWNER/REPO/source-driven-development

Суть: проверять актуальные официальные источники перед framework-specific решениями.

Что взять:

- Если изменение зависит от нестабильного API, новой версии библиотеки, framework conventions или депрекейта, проверь официальную документацию.
- Не реализуй по памяти то, что могло измениться: routing APIs, auth adapters, config formats, migration steps, deployment/runtime behavior.
- В финале кратко упоминай, что было проверено, если внешняя документация повлияла на код.

Что не брать:

- Требование цитировать источники для каждой обычной локальной правки.
- Длинные research reports внутри implementation-этапа.

### `addyosmani/agent-skills@debugging-and-error-recovery`

Источник: https://skilld.dev/skills/addyosmani/agent-skills/debugging-and-error-recovery

Суть: при сбое остановить расширение скоупа и диагностировать причину.

Что взять:

- Если сборка, линтер, runtime или ручная проверка ломаются, прекрати добавлять новую функциональность.
- Сохрани короткое evidence: команда, ошибка, затронутый файл, наблюдаемое поведение.
- Диагностируй минимальную причину и исправляй ее, не смешивая с новым скоупом.
- Если ошибка вне текущей задачи, вынеси ее пользователю или в хвост.

Что не брать:

- Полный incident workflow.
- Обязанность чинить все обнаруженные проблемы проекта.

### `addyosmani/agent-skills@code-review-and-quality`

Источник: https://github.com/addyosmani/agent-skills/blob/main/skills/code-review-and-quality/SKILL.md

Суть: финальная проверка изменения по нескольким осям качества.

Что взять:

- Легкий self-check перед завершением: correctness, readability, architecture fit, security, performance.
- Проверяй, что изменение следует локальным паттернам и не вводит случайную абстракцию.
- Для user input, auth, data access и external data всегда учитывай базовую безопасность.
- Не отмечай чекбокс выполненным, если поведение не реализовано фактически.

Что не брать:

- Полный code review report как результат `implement`.
- Pre-merge процесс, PR-ритуалы и approval language.

### `github/awesome-copilot@refactor`

Источник: https://skills.sh/github/awesome-copilot/refactor

Суть: структурные улучшения без изменения поведения.

Что взять:

- Не смешивай широкую чистку кода с реализацией фичи.
- Разрешай локальный рефакторинг только когда он нужен для заявленного изменения.
- Делай маленькие структурные правки: extract function, remove duplication, name constants, simplify conditionals.

Что не брать:

- Отдельную большую refactoring-программу.
- Требование предварительно создавать или расширять тесты в `implement`.

### `github/awesome-copilot@breakdown-feature-implementation`

Источник: https://claudemarketplaces.com/skills/github/awesome-copilot/breakdown-feature-implementation

Суть: превращение требований в подробный implementation blueprint.

Что взять:

- Перед кодом полезно проверить, что есть техническая карта: frontend, backend, data model, API, deployment constraints, risks.
- Если такой карты нет для сложной фичи, `implement` должен остановиться и отправить работу в `planning` или `task`.

Что не брать:

- Генерацию подробного blueprint внутри `implement`.
- Mermaid-диаграммы, issues, deployment strategy и полное описание архитектуры.

### `bmad-code-org/bmad-method@bmad-check-implementation-readiness`

Источник: https://skills.sh/bmad-code-org/bmad-method/bmad-check-implementation-readiness

Суть: проверка готовности требований, UX, архитектуры и backlog перед реализацией.

Что взять:

- Мини-гейт готовности: требования понятны, архитектура не противоречит задаче, зависимости известны, блокеров нет.
- Для UI-задач проверь наличие `design.md` или проектного `./workflow/DESIGN.md`, если внешний вид влияет на реализацию.
- Для архитектурных изменений проверь `./workflow/ARCHITECTURE.md`, если он есть.

Что не брать:

- Adversarial audit всех документов перед каждой задачей.
- Роль отдельного архитектора или PM внутри implementation-этапа.

### `davila7/claude-code-templates@task-execution-engine`

Источник: https://skills.sh/davila7/claude-code-templates/task-execution-engine

Суть: пошаговое исполнение задач с фиксацией прогресса.

Что взять:

- Работай по одному выбранному пункту, пока он не завершен или не заблокирован.
- После выполнения синхронизируй состояние артефактов: чекбоксы, статус фичи, хвосты.
- Не распараллеливай зависимые правки без необходимости.

Что не брать:

- Отдельный task engine, очередь, subagent orchestration и внешние таск-трекеры.

## Фильтр применимости

Добавляй в `implement` только то, что помогает надежно превратить уже выбранный скоуп в продуктовый код.

Подходит:

- readiness-проверка перед правкой;
- выбор источника скоупа: `NN-task.md`, `plan.md`, простая `feature.md`;
- точечная загрузка контекста;
- поиск локальных паттернов перед реализацией;
- инкрементальная правка;
- доступная проверка результата без создания тестового канона;
- остановка на неоднозначности;
- обновление чекбоксов и статуса фичи;
- фиксация хвостов, если часть работы требует другого этапа.

Не подходит:

- создание нового плана сложной фичи;
- переписывание `plan.md` вместо `planning` или `improve`;
- написание `tests.md`;
- написание тестового кода как основная обязанность;
- документация пользователя или разработчика;
- большой refactor без прямой связи с задачей;
- создание issues, PR, веток, коммитов;
- deployment и release checklist.

## Рекомендуемый алгоритм `implement`

1. Определи фичу и рабочий скоуп.
2. Прочитай `./workflow/features/{slug}/feature.md`.
3. Если есть `./workflow/features/{slug}/NN-task.md`, работай по нему.
4. Если task-файла нет, но есть `plan.md`, выбери ближайший невыполненный пункт или явно указанный пользователем пункт.
5. Если плана нет, работай напрямую по `feature.md` только для простой фичи с понятным результатом.
6. Прочитай `design.md`, `./workflow/DESIGN.md`, `./workflow/ARCHITECTURE.md`, `./workflow/PROJECT.md`, если они влияют на изменение.
7. Найди файлы, которые нужно менять, и локальный пример похожего паттерна.
8. Сформулируй короткий execution outline для себя: что меняется, где, чем проверить.
9. Реализуй минимальный законченный срез поведения.
10. Проверь доступным способом: build, lint, typecheck, existing tests, ручная проверка или статический просмотр кода.
11. Если проверка ломается, останови расширение скоупа, диагностируй и исправь причину в рамках задачи.
12. Повтори цикл для следующего среза.
13. Отметь чекбокс в `plan.md` только после фактической реализации соответствующего пункта.
14. Если вся фича реализована, обнови статус в `./workflow/PLAN.md` на `[x]`.
15. Если остались вопросы для `test`, `docs`, `planning`, `design` или пользователя, запиши их как хвосты, не маскируя незавершенную работу.

## Мини-гейт готовности перед правкой

- Есть понятный источник скоупа: `NN-task.md`, `plan.md` или простая `feature.md`.
- Понятно, какое поведение должно появиться.
- Понятно, какие ограничения дает дизайн, архитектура и проектный стек.
- Найден хотя бы один локальный паттерн или понятно, почему его нет.
- Рискованные действия определены заранее: schema changes, dependency changes, auth/security, data migration, destructive operations.
- Для рискованных действий есть явное основание в задаче или вопрос пользователю.

## Правила синхронизации прогресса

- Не отмечай пункт выполненным по намерению, только по факту работающего кода.
- Если пункт частично выполнен, оставь чекбокс пустым и добавь короткий хвост.
- Если задача выполнена иначе, чем написано в плане, обнови формулировку так, чтобы артефакт отражал настоящее состояние.
- Если найден новый обязательный подпункт, добавь его в `plan.md` как незавершенный хвост.
- Статус `[x]` в `./workflow/PLAN.md` ставится только когда весь implementation scope фичи завершен.

## Легкий self-check перед завершением

- Correctness: заявленное поведение реализовано, edge cases текущего скоупа не проигнорированы.
- Fit: код следует локальным паттернам, именованию и границам модулей.
- Simplicity: нет лишней абстракции, широкой чистки и несвязанного переписывания.
- Safety: user input, auth, secrets, external data и destructive actions обработаны осторожно.
- Verification: выполнена доступная проверка или явно указано, почему ее нельзя выполнить.
- Workflow: чекбоксы, статус фичи и хвосты отражают фактическое состояние.
