# improve

## Назначение

Проверочный второй проход по `./workflow/features/{slug}/plan.md` для сложных или архитектурно важных фич — часто другой моделью, чем та, что планировала. Сверяет план с брифом, каноном workflow и реальной кодовой базой и вносит минимальные точечные правки: фантомные пути, скрытые зависимости, дыры в порядке работ, лишний scope. Это рецензент с ручкой, а не второй планировщик.

## Место в конвейере

После `planning` (и `design`, если он был). Структуру, язык и режим плана, заданные `planning`, сохраняет — правит только содержание ошибок. Полная перезапись — лишь когда план фундаментально вводит в заблуждение, и только с подтверждения пользователя. Дальше: большой многофазный план → `task`; компактный → `implement`.

## Входы

- `./workflow/features/{slug}/feature.md` и `plan.md` — оба обязательны
- `design.md` фичи, если есть
- канон `./workflow/`, когда релевантен
- кодовая база — проверка каждого пути, модуля и зависимости, названных планом

## Выходы

- точечно исправленный `plan.md` в прежней структуре
- при необходимости — служебные хвосты в `./workflow/PLAN.md` (статус фичи остаётся `[-]`)
- короткий список правок в чате и рекомендация следующего шага

## Не делает

- Не меняет структуру и язык плана.
- Не пишет `tests.md`, `NN-task.md`, код, документацию, отчётные файлы.
- Не расширяет scope за пределы брифа — спекулятивное удаляет.
- Не делает git-операций.

## Когда применять

Когда план сложной фичи стоит проверить свежим взглядом перед `task` или `implement`. Чистый проход без находок — валидный результат: скил сообщает, что план надёжен, и рекомендует следующий шаг.
