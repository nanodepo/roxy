# improve

## Назначение

`improve` делает второй проход по плану фичи. Скил ищет дыры, неверные зависимости, лишний скоуп и слабые формулировки, затем улучшает только `plan.md`.

## Ответственность

- Прочитать `feature.md`, `plan.md` и релевантный проектный контекст.
- Повторно исследовать кодовую базу.
- Переписать `./workflow/features/{slug}/plan.md` целиком или точечно, если так безопаснее для текущего формата.
- Добавить в `PLAN.md` служебный хвост для `test`, если улучшение плана выявило тестовый риск.
- Обновить только служебный статус или служебные хвосты в `./workflow/PLAN.md`.

## Связь с конвейером

`improve` работает после `planning` и, если нужно, после `design`. Его улучшенный `plan.md` становится входом для `task` и `implement`.

## Почему граница такая

Второй проход нужен для качества плана, а не для расширения зоны ответственности. Тестовые и документационные идеи могут быть только служебными хвостами; владеют ими `test` и `docs`.

## Входной контекст

- `./workflow/features/{slug}/feature.md`
- `./workflow/features/{slug}/plan.md`
- `./workflow/features/{slug}/design.md`, если есть
- проектные workflow-документы
- кодовая база проекта

## Выходные артефакты

- улучшенный `./workflow/features/{slug}/plan.md`
- служебные хвосты в `./workflow/PLAN.md`

## Не делает

- Не пишет `tests.md`.
- Не создаёт `NN-task.md`.
- Не пишет код.
- Не пишет документацию.
- Не делает git-операции.

## Критерий готовности

План стал исполнимее, самодостаточнее и чище по границам ответственности, а тестовые идеи не смешаны с планом реализации.
