# REFERENCES.md

## Цель исследования

Исследованы скилы из открытой экосистемы, близкие к `initialize` по роли: подготовка проекта к агентному workflow, первичный сбор технического контекста, создание постоянных документов и маршрутизация следующих шагов.

`initialize` остается легким bootstrap-скилом: он создает `./workflow/`, фиксирует техническую справку в `PROJECT.md` и оставляет хвосты в `PLAN.md`. Он не принимает продуктовые, архитектурные, визуальные и git-решения.

## Как искали

Использован `$find-skills`, то есть Skills CLI:

- `npx skills find "project initialization"`
- `npx skills find "project context"`
- `npx skills find "repository analysis"`
- `npx skills find "workflow setup"`
- `npx skills find "project onboarding"`
- `npx skills find "documentation bootstrap"`
- `npx skills find "project memory"`
- `npx skills find "spec setup"`

Дополнительно изучены открытые страницы и `SKILL.md` найденных кандидатов, когда одной выдачи было недостаточно для оценки.

## Близкие скилы

### `mingyuepop/specforge@project-initialization`

Источник: https://skills.sh/mingyuepop/specforge/project-initialization

Суть: скил читает готовые `specs/`-документы и превращает их в каркас проекта. Полезен как пример строгой границы: исполнитель не делает технических решений, которые не описаны в документах.

Что полезно для `initialize`:

- перед записью артефактов сначала установить проектный контекст;
- явно различать новый и уже существующий проект;
- при существующем проекте выполнять безопасное обновление документов, а не пересоздавать структуру;
- фиксировать результат выполнения в коротком артефакте.

Что не подходит:

- создание каркаса приложения;
- `git init`;
- генерация `.gitignore`, `.env.example`, `README.md`;
- работа от готовых `specs/`, потому что в `roxy` канон лежит в `./workflow/`.

### `mingyuepop/specforge@project-context-initialization`

Источник: https://skills.sh/mingyuepop/specforge/project-context-initialization

Суть: brownfield-подключение существующего проекта через сканирование кода, зависимостей, README и конфигов с последующей генерацией глобальных документов.

Что полезно для `initialize`:

- читать package manifests, lock-файлы, языковые конфиги, Docker/CI и тестовые конфиги как первичные источники;
- использовать README только как вспомогательный источник, а не как источник истины;
- если сведений недостаточно, оставлять явные вопросы в документе;
- отделять наблюдаемые факты от предположений.

Что не подходит:

- генерация продуктового описания;
- генерация полного набора спецификаций;
- автоматическое заполнение бизнес-видения.

### `aspiers/ai-config@project-initialization`

Источник: https://skills.sh/aspiers/ai-config/project-initialization

Суть: инициализация репозитория для совместимости разных AI-агентов через `AGENTS.md`/`CLAUDE.md` и проверку опасных git-инструкций.

Что полезно для `initialize`:

- идея единого канонического места для правил и контекста;
- проверка существующих агентных инструкций перед созданием новых документов;
- принцип discoverability: артефакт должен быть найден следующим агентом без знания истории выполнения.

Что не подходит:

- правка `AGENTS.md` или `CLAUDE.md`;
- создание symlink;
- исправление git-команд внутри инструкций.

### `bmad-code-org/bmad-method@bmad-generate-project-context`

Источник: https://skills.sh/bmad-code-org/bmad-method/bmad-generate-project-context

Суть: генерация `project-context.md` с критическими правилами реализации для AI-агентов. Фокус на коротких, неочевидных правилах, которые LLM не должен выводить из общих best practices.

Что полезно для `initialize`:

- фиксировать версии технологий, package manager и значимые инструменты;
- искать конфиги сборки, линтинга, форматирования и тестов;
- выделять только то, что влияет на дальнейшую работу агентов;
- не документировать универсальные советы;
- помечать неизвестные или конфликтующие факты как вопросы к пользователю.

Что не подходит:

- интерактивная многошаговая генерация правил;
- глубокое извлечение naming conventions и code patterns;
- отдельный `project-context.md`, потому что в `roxy` эту роль частично выполняют `PROJECT.md`, `ARCHITECTURE.md` и будущие feature-документы.

### `wshobson/agents@context-driven-development`

Источник: https://skills.sh/wshobson/agents/context-driven-development

Суть: методология, где контекст проекта является управляемым артефактом рядом с кодом: product, tech stack, workflow, tracks.

Что полезно для `initialize`:

- мысль "context precedes code" хорошо совпадает с назначением bootstrap;
- каждый тип информации имеет одно каноническое место;
- `tech-stack` и `workflow` стоит держать синхронными с реальными файлами проекта;
- перед реализацией фичи контекст должен быть проверен на актуальность.

Что не подходит:

- отдельный `conductor/`-контур;
- `product.md`, `product-guidelines.md`, `tracks.md`;
- полноценное управление work units внутри `initialize`.

### `github/awesome-copilot@repo-story-time`

Источник: https://skills.sh/github/awesome-copilot/repo-story-time

Суть: repository archaeology: техническая сводка плюс история репозитория из git history.

Что полезно для `initialize`:

- системный обход репозитория через документы, конфиги, исходники, тесты и сборочные файлы;
- техническая сводка должна отвечать на вопросы "что это", "как запустить", "чем собрано", "где основные части".

Что не подходит:

- анализ git history;
- повествовательная история проекта;
- файлы `REPOSITORY_SUMMARY.md` и `THE_STORY_OF_THIS_REPO.md`.

### `patricio0312rev/skills@dev-onboarding-builder`

Источник: https://skills.sh/patricio0312rev/skills/dev-onboarding-builder

Суть: создание подробного onboarding-документа для разработчиков: prerequisites, setup, troubleshooting, first task, codebase tour.

Что полезно для `initialize`:

- `PROJECT.md` может содержать краткий блок "как поднять проект";
- полезны секции про prerequisite tools, env vars, команды запуска, тесты и частые локальные ограничения;
- troubleshooting допустим только как короткие known gaps, если они обнаружены в проекте.

Что не подходит:

- оценки времени;
- команда, роли, менторы;
- first task;
- подробный codebase tour.

### `ctsstc/get-shit-done-skills@gsd:init-repo`

Источник: https://skills.sh/ctsstc/get-shit-done-skills/gsd

Суть: создание структуры методологии разработки: planning-директория, docs и команды.

Что полезно для `initialize`:

- минимальная структура должна создаваться предсказуемо;
- критерий готовности должен проверять наличие директорий и стартовых документов.

Что не подходит:

- создание `.claude/`;
- `git init`;
- расширенная система команд и агентов.

## Идеи, которые усиливают `initialize`

### 1. Явная модель источников для `PROJECT.md`

`initialize` стоит читать источники в таком порядке:

1. package manifests и lock-файлы;
2. языковые и build-конфиги;
3. Docker, Compose, devcontainer, CI-файлы;
4. тестовые, lint и format-конфиги;
5. env templates;
6. README и docs как вспомогательный контекст;
7. ответы пользователя для неизвестных мест.

Это не перегружает скил, потому что он уже отвечает за технический контекст.

### 2. Короткий канон секций `PROJECT.md`

Минимальный полезный набор:

- название и тип проекта, если они надежно определены;
- стек и версии;
- package manager и основные команды;
- запуск локально;
- тесты;
- сборка;
- lint/format/typecheck;
- env и внешние сервисы;
- Docker/CI/deploy, если обнаружены;
- открытые вопросы.

Секции без данных можно не заполнять или оставлять коротким `Требует уточнения`.

### 3. Разделение фактов и догадок

В `PROJECT.md` стоит записывать только наблюдаемые факты. Если стек, команда запуска или сервисы не определяются из файлов, скил задает вопрос пользователю или оставляет хвост в `PLAN.md`.

### 4. Идемпотентное обновление

Если `./workflow/` уже существует, `initialize` должен:

- не перетирать пользовательский текст;
- дополнять отсутствующие технические секции;
- сохранять существующие хвосты в `PLAN.md`;
- добавлять новые хвосты только для реально отсутствующих артефактов.

### 5. Хвосты в `PLAN.md` как маршрутизация

`PLAN.md` остается легким маршрутизатором:

- `roadmap`, если нет `VISION.md` или `ROADMAP.md`;
- `architecture`, если нет `ARCHITECTURE.md`;
- `design-guideline`, если нет `DESIGN.md`;
- уточнение технического контекста, если `PROJECT.md` содержит открытые вопросы.

### 6. Контекст для следующих агентов

`PROJECT.md` должен быть написан так, чтобы следующий агент мог начать работу без истории чата:

- где проект;
- как его запустить;
- как проверить изменения;
- какие инструменты уже выбраны;
- какие решения не приняты.

## Идеи, которые стоит оставить за границей `initialize`

- Выбор архитектурного паттерна.
- Продуктовое видение, roadmap и success metrics.
- Дизайн, brand voice и пользовательская коммуникация.
- Генерация feature/spec/task-документов.
- Создание каркаса приложения.
- Изменение `AGENTS.md`, `CLAUDE.md`, `.claude/`, git hooks или symlink.
- Git-операции.
- Глубокий аудит кода, commit history и ownership.
- Полный onboarding-документ.

## Рекомендация для будущей правки `SKILL.md`

Добавить в `initialize` три компактных блока:

1. **Сбор технического контекста**: перечислить источники, которые нужно проверить перед записью `PROJECT.md`.
2. **Шаблон `PROJECT.md`**: задать короткие секции, которые заполняются только наблюдаемыми фактами.
3. **Правила безопасного обновления**: не перетирать существующие документы, сохранять пользовательский текст, добавлять только отсутствующие хвосты.

Этого достаточно, чтобы усилить скил практиками из найденных аналогов и не превратить bootstrap в отдельную методологию, аудит или генератор проекта.
