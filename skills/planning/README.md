# planning

## Назначение

Превращает фичевый бриф в план реализации `./workflow/features/{slug}/plan.md` и помечает фичу `[-]` в `./workflow/PLAN.md`. План нужен для работы, которую агент не вытянет за один проход: он разбивает процесс на фазы с проверяемыми результатами. План направляет исполнителя, а не диктует шаги: чекбоксы — результаты, не микрошаги.

## Место в конвейере

После `feature`. Дальше по плану: компактный план → `implement`; UI с нетривиальным UX → `design`; сложная или архитектурно важная фича → `improve` как проверочный проход; большой многофазный план → `task`. Структуру плана сохраняет `improve` — он правит точечно, не пересобирая.

## Входы

- `./workflow/features/{slug}/feature.md` — источник смысла и границ
- `design.md` фичи, если есть
- канон `./workflow/` (`PROJECT.md`, `ARCHITECTURE.md`, `DESIGN.md`, `PLAN.md`)
- кодовая база — только чтение, для проверенного контекста

## Выходы

- `./workflow/features/{slug}/plan.md`: Goal, Context, Decisions, Phases (или плоские Steps), Tails — только секции, несущие решения
- статус `[-]` у фичи в `./workflow/PLAN.md`
- рекомендация следующего шага в чате

## Не делает

- Не пишет `tests.md`, `design.md`, `NN-task.md`, код и документацию.
- Не меняет продуктовый код.
- Не пересказывает `feature.md`.
- Не делает git-операций.

## Когда применять

Когда у фичи есть бриф, а работа слишком велика для прямой реализации. Простую фичу скил не раздувает: плоский список шагов или честная рекомендация идти сразу в `implement`. Размер плана пропорционален сложности — пары предложений и короткого списка шагов достаточно для простой фичи.
