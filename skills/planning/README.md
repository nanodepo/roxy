# planning

## Назначение

`planning` превращает `feature.md` в план реализации. Скил отвечает только за `plan.md` и не заходит в тестовый домен.

## Ответственность

- Прочитать `feature.md` и релевантный проектный контекст.
- Проанализировать кодовую базу настолько глубоко, насколько нужно для реалистичного плана.
- Создать или обновить `./workflow/features/{slug}/plan.md`.
- Описать фазы, задачи, файлы, зависимости, риски и открытые вопросы.
- Обновить служебный статус фичи в `./workflow/PLAN.md` на `[-]`.

## Связь с конвейером

`planning` получает вход от `feature`. Его `plan.md` читают `design`, `improve`, `task`, `implement`, `test` и `docs`.

## Почему граница такая

План реализации отвечает на вопрос “как делать”, но не должен заранее владеть тестовым планом или фичевым UI-решением. Статус в `PLAN.md` только отражает готовность плана для следующего этапа.

## Входной контекст

- `./workflow/features/{slug}/feature.md`
- `./workflow/PROJECT.md`
- `./workflow/ARCHITECTURE.md`
- `./workflow/DESIGN.md`, если фича затрагивает UI
- кодовая база проекта

## Выходные артефакты

- `./workflow/features/{slug}/plan.md`
- обновлённый служебный статус в `./workflow/PLAN.md`

## Не делает

- Не пишет `tests.md`.
- Не пишет фичевый `design.md`.
- Не создаёт `NN-task.md`.
- Не пишет код.
- Не делает git-операции.

## Критерий готовности

План можно передать в `design`, `improve` или `task` без дополнительного пересказа контекста.
