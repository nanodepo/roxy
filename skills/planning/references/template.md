# Шаблоны и формат

Подгружается на этапе 7 (запись `plan.md`) и этапе 8 (запись `tests.md`).

## Шаблон `plan.md`

```markdown
# План: {Название фичи}

Дата: {YYYY-MM-DD}

## Настройки
- Логирование: verbose | standard | minimal
- Особые требования: {текст пользователя или «нет»}

## Контекст
{1–3 коротких абзаца. Выдержка из feature.md и проектного контекста.
Не пересказывай feature.md целиком — это база, не копия.}

## Затронутые компоненты
- `path/to/file.ext` — {роль файла}
- `path/to/module/` — {роль модуля}

## Задачи

### Фаза 1: {Название фазы}

- [ ] Задача 1: {краткий заголовок}
  - **Что делаем**: {1–2 предложения о результате и поведении}
  - **Файлы**: `path/to/file1.ext`, `path/to/file2.ext`
  - **Логирование**: {что логировать, на каком уровне, формат}
  - **Зависимости**: нет

- [ ] Задача 2: ...

### Фаза 2: {Название фазы}

- [ ] Задача 3: ...
  - **Зависимости**: задача 1, задача 2

## Открытые вопросы

<!-- Секция опускается, если открытых вопросов нет -->

- {Формулировка вопроса.} — требует уточнения у пользователя.
```

## Шаблон `tests.md`

```markdown
# Тесты: {Название фичи}

Дата: {YYYY-MM-DD}

## Базовые сценарии

### {invariant_name_snake_case}

{1–2 предложения: что проверяется и почему этот инвариант важен.}

### {invariant_name_snake_case}

...
```

## Пример описания задачи

```markdown
- [ ] Задача 3: Реализовать эндпоинт логина пользователя
  - **Что делаем**: POST `/api/auth/login` принимает email и пароль,
    валидирует через сервис аутентификации, возвращает JWT при успехе
    и 401 при невалидных данных.
  - **Файлы**: `src/api/auth/login.ts`, `src/services/auth.ts`
  - **Логирование**: вход функции с контекстом запроса (DEBUG),
    результат валидации (INFO для успеха, WARN для отказа),
    ошибки с полным контекстом (ERROR). Формат: `[Module.method] message {data}`.
  - **Зависимости**: задача 1 (модели пользователя), задача 2 (JWT-утилита).
```

## Чек-лист для каждой задачи

Каждая запись задачи указывает:

- Результат и ожидаемое поведение.
- Пути к файлам, которые создаются или меняются.
- Требования к логированию: что логировать, где, на каком уровне.
- Зависимости от других задач (если применимо).

Без требований к логированию задача неполна.

## Имена сценариев в `tests.md`

Хороший смысл:

```
guest_cannot_delete_project
primary_action_is_available_from_toolbar
checkout_requires_confirmed_payment_method
billing_period_starts_on_first_business_day
```

Плохой смысл:

```
removed_old_delete_button
button_no_longer_in_right_panel
fixes_bug_1234
getter_returns_set_value
modulo_returns_remainder
```

Имя кодирует продуктовый инвариант, а не инцидент или языковую операцию.

## Размер и тон

- `plan.md` подробный, без раздувания. Каждая секция существует, потому что без неё агент-имплементатор не сможет действовать.
- `tests.md` лаконичный. Чем меньше сценариев, тем лучше — покрываем только базовую бизнес-логику и нетривиальные инварианты.
- Тон обоих файлов — текущая реальность («Эндпоинт возвращает JWT»), а не история обсуждений («Решили использовать JWT, потому что...»).
