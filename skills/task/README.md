# task

## Назначение

`task` разбивает план фичи на самодостаточные задачи для последовательной реализации. Скил владеет `NN-task.md` и навигационной нормализацией `plan.md`.

## Ответственность

- Прочитать `feature.md`, `plan.md` и `design.md`, если он есть.
- Создать `NN-task.md` для задач, которые можно выполнять по одной.
- Переписать `plan.md` как карту фаз и задач, если это делает дальнейшую работу яснее.
- Обновить служебный статус фичи в `./workflow/PLAN.md` на `[+]`.

## Связь с конвейером

`task` работает после `planning` или `improve`. Его задачи выполняет `implement`; `test` и `docs` могут читать их для понимания фактического скоупа.

## Почему граница такая

Декомпозиция отвечает за удобную нарезку работы. Нормализация `plan.md` допустима только как карта к созданным задачам; статус в `PLAN.md` только показывает, что фича готова к пошаговой реализации.

## Входной контекст

- `./workflow/features/{slug}/feature.md`
- `./workflow/features/{slug}/plan.md`
- `./workflow/features/{slug}/design.md`, если есть

## Выходные артефакты

- `./workflow/features/{slug}/NN-task.md`
- обновлённый `./workflow/features/{slug}/plan.md`
- обновлённый служебный статус в `./workflow/PLAN.md`

## Не делает

- Не пишет код.
- Не пишет `tests.md`.
- Не меняет проектные workflow-документы, кроме статуса фичи и служебных хвостов.
- Не делает git-операции.

## Критерий готовности

Каждая задача имеет понятный вход, цель, границы файлов и ожидаемый результат без зависимости от устной истории.
