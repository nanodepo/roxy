# REFERENCES.md

## Назначение

Справка фиксирует идеи из похожих testing-скилов, которые могут усилить `test` без превращения его в отдельный QA-фреймворк или справочник по конкретному стеку.

`test` остается владельцем `tests.md`, тестового кода и факта успешного тестового прогона. Он работает после `implement`, опирается на реализованное поведение и не меняет продуктовый код.

## Что стоит встроить в `test`

### 1. Выбор уровня проверки

Перед написанием тестов определить минимальный уровень, который доказывает инвариант:

- unit — чистая логика, валидация, преобразования, ветвления;
- integration — взаимодействие модулей, API, база данных, внешние адаптеры;
- component/UI — состояние компонента, события, доступность важного пользовательского действия;
- e2e — только критичный пользовательский путь или сквозная связка, которую нельзя доказать дешевле.

E2E не заменяет unit и integration. Unit-тест не доказывает пользовательский путь. Выбирай самый дешевый тест, который уверенно ловит нарушение инварианта.

### 2. Структура `tests.md`

`tests.md` лучше вести как карту проверяемого поведения:

- инвариант;
- риск, который он закрывает;
- тип теста;
- файл теста или команда;
- результат запуска;
- непокрытые зоны, если они остаются.

Формулировки должны описывать текущее поведение системы. Не записывать историю исправления, причины появления бага или заметки вида "теперь работает".

### 3. Discovery перед тестами

Перед изменениями:

- прочитать `./workflow/PROJECT.md` и найти команды тестов;
- определить существующий тестовый фреймворк по конфигам, lock-файлам, package scripts, pytest config, test directories;
- посмотреть стиль соседних тестов: naming, fixtures, helpers, mocks, test data;
- выбрать место для нового теста по локальным правилам проекта.

Если команда тестов не описана, вывести ее из фактического стека и зафиксировать выбранную команду в `tests.md`.

### 4. Качество теста

Хороший тест:

- проверяет поведение, а не внутреннюю реализацию;
- имеет понятное имя по инварианту;
- независим от порядка запуска;
- сам готовит и очищает состояние;
- использует реальные зависимости там, где это дешево и надежно;
- мокает только внешние, дорогие, нестабильные или недоступные зависимости;
- не зависит от времени, сети, случайности и shared state без явного контроля;
- использует параметризацию для однотипных граничных случаев.

### 5. Web UI и Playwright

Для динамического web UI:

- сначала запустить или найти локальный сервер;
- дождаться стабильного состояния страницы;
- при необходимости снять screenshot или прочитать rendered DOM;
- выбрать стабильные селекторы: role, label, text, test id;
- проверять пользовательское действие и видимый результат;
- сохранять trace, screenshot или лог только если это уже принято в проекте или нужно для диагностики.

Не добавлять Playwright как обязательный слой, если существующий стек уже доказывает поведение дешевле.

### 6. Регрессии

Для бага или подозрительной зоны:

- сформулировать инвариант, который должен сохраняться;
- написать тест, который воспроизводит нарушение поведения;
- убедиться, что тест действительно способен падать по ожидаемой причине, если это можно проверить без правки продуктового кода;
- после исправления или существующей реализации запустить тест и зафиксировать результат.

Тест называется по нормальному поведению, а не по инциденту.

### 7. Проверка перед статусом `[*]`

Статус `[*]` в `./workflow/PLAN.md` допустим только после свежего запуска проверочной команды.

Перед обновлением статуса:

- определить команду, которая доказывает готовность;
- запустить ее полностью или явно ограничить область и записать причину ограничения;
- прочитать exit code и вывод;
- убедиться, что заявленный результат совпадает с фактом;
- записать команду и результат в `tests.md`.

Если тесты не запущены или команда падает, статус не становится `[*]`.

## Что не стоит переносить

- Обязательный TDD-цикл для всей фичи: `test` работает после реализации и не должен требовать удаления продуктового кода.
- Большие справочники по pytest, Jest, Vitest, Playwright и CI/CD: скил должен подстраиваться под проект, а не навязывать стек.
- Обязательные проценты покрытия: важнее закрыть инварианты и рисковые ветки.
- Полную cross-browser, performance, security, accessibility матрицу для каждой фичи: включать только при явной связи с поведением фичи.
- Генерацию тестов из структуры кода без чтения `feature.md`, `plan.md`, задач и фактического поведения.

## Короткий чеклист для будущего `SKILL.md`

1. Прочитай feature context, `PROJECT.md`, существующие тесты и фактический код.
2. Выпиши инварианты поведения и риски.
3. Выбери самый дешевый уровень проверки для каждого инварианта.
4. Напиши или обнови тесты в стиле проекта.
5. Запусти релевантную проверочную команду.
6. Запиши в `tests.md`: инварианты, файлы, команду, результат, остаточные пробелы.
7. Обнови `./workflow/PLAN.md` на `[*]` только при успешном свежем прогоне.
