# Стадия 1: Change Summary

> Когда читать: при запуске режима `change-summary` или как первая стадия полного цикла.

Цель — понять, что реализовано в фиче и что заслуживает проверки тестами. Стадия не пишет файл; результат остаётся в контексте сессии и используется следующими стадиями.

## Шаг 1. Загрузить контекст

К этому моменту уже прочитаны (этап 2 SKILL.md):
- `feature.md` — что и зачем
- `plan.md` — задачи и их статус (отметки `[x]` — выполненные)
- `NN-task.md` (все, что есть) — детальные задачи
- `tests.md` (если есть) — базовый план тестирования

Есть отметки `[x]` в `plan.md` или существуют `NN-task.md` → реализация уже произошла. Найди соответствующий код через `Glob` / `Grep` по упоминаниям из задач.

## Шаг 2. Изучить код реализации

Для каждой выполненной задачи определи затронутые файлы и прочитай ключевые места. Не читай всё подряд — фокус:
- бизнес-логика (services, use-cases, domain layer);
- контракты (типы, интерфейсы, схемы валидации, API-маршруты);
- места, где изменилось поведение пользователя.

Skip: lock-файлы, сгенерированный код, форматирование, миграции без логики.

## Шаг 3. Анализ через `mcp__sequential-thinking__sequentialthinking`

Пройди по разделам:

**Что реализовано:**
- компоненты добавлены / изменены / удалены;
- пользовательские сценарии открылись или изменились;
- какие данные начали течь по системе или поменяли формат.

**Функциональные риски:**
- какая бизнес-логика добавлена или изменена;
- входы/выходы (форматы, валидация, структура);
- сценарии пользователя, зависящие от изменений.

**Технические риски:**
- схема данных (БД, API-контракты, файловые форматы, хранилище);
- конфигурация, переменные окружения;
- обработка ошибок и поведение на границах;
- интеграции с внешними сервисами;
- авторизация, контроль доступа, безопасность.

**Регрессионные риски:**
- существующая функциональность под угрозой;
- смежные фичи, требующие перепроверки.

**Полнота `tests.md` (если есть):**
- покрывает ли план все продуктовые инварианты;
- что упущено;
- что устарело или неактуально.

## Шаг 4. Зафиксировать вывод в контексте

Сформулируй компактный итог (5–15 строк) для стадии `test-plan`:

- основные затронутые компоненты;
- ключевые продуктовые инварианты, защищаемые тестами;
- риски с приоритетом (`высокий` / `средний` / `низкий`);
- участки без тестов (тривиально / гарантировано типами / гарантировано стандартной библиотекой);
- открытые вопросы.

Итог — рабочий вход для `test-plan`. Стадия запущена в режиме `change-summary` отдельно → покажи итог пользователю в чате.

## Что НЕ делать

- Не писать `change-summary.md` файл; он не нужен в `./workflow/`.
- Не уходить в описание «что было до изменений» — фокус на актуальном состоянии.
- Не предлагать тесты на этой стадии; только анализ. Тесты → `test-plan` и `test-cases`.
- Не проводить git-операции (см. жёсткие правила SKILL.md).
