# Стадия 3: Test Cases

> Когда читать: при запуске режима `test-cases` или как третья стадия полного цикла.

Цель — превратить чек-лист инвариантов из `tests.md` в код тестов в проекте.

## Шаг 1. Подготовить вход

Прочитай `./workflow/features/{slug}/tests.md`.

`tests.md` отсутствует → остановись, сообщи: сначала прогнать стадию `test-plan` или дать готовый `tests.md`.

К этому моменту фреймворк, каталог тестов и команда запуска уже определены (этап 3 SKILL.md): `test_framework`, `test_dir`, `test_run_command`.

## Шаг 2. Изучить стиль существующих тестов

В `test_dir` есть тесты → прочитай 2–3 для понимания:
- структура файла теста (один или много кейсов на файл);
- стиль именования (snake_case / camelCase, префиксы, описательные строки);
- паттерн фикстур (setUp/tearDown, фикстуры pytest, помощники);
- паттерн моков и подмен;
- расположение по модулям проекта.

Не нашлось тестов → следуй идиомам выбранного фреймворка по умолчанию.

## Шаг 3. Спроектировать тесты по чек-листу

Для каждой строки чек-листа инвариантов из `tests.md`:

1. Определи единицу тестирования (функция / метод / endpoint / use-case).
2. Выбери уровень: unit / integration / e2e — по природе инварианта, не по умолчанию.
3. Сформулируй имя теста — про инвариант, в стиле проекта.
4. Опиши preconditions, действие, ожидаемый результат — конкретно, без «валидные данные».

**Группировка кейсов:**

- *Позитивные сценарии* — стандартное использование с валидными данными, основные пользовательские пути.
- *Негативные сценарии* — невалидные входы, нарушение бизнес-правил, отсутствие зависимостей.
- *Граничные случаи* — минимумы и максимумы, пустые строки, ноль, null, очень длинные строки, спец-символы, конкурентные запросы (если применимо).
- *Регрессионные проверки* — смежная функциональность, интеграции с другими частями системы.

Высокоприоритетные инварианты (`High` в `tests.md`) — обязательны. Низкоприоритетные — опциональны: пиши их только если они защищают реальный инвариант, не покрывают тривиальное.

## Шаг 4. Написать код тестов

Каждый файл — `Write` в `test_dir` по принятой структуре проекта.

**Имена тестов — про инвариант:**

Хорошо:
```
guest_cannot_delete_project
primary_action_is_available_from_toolbar
checkout_requires_confirmed_payment_method
billing_period_starts_on_first_business_day
duplicate_payment_does_not_create_second_charge
```

Плохо:
```
removed_old_delete_button
button_no_longer_in_right_panel
fixes_bug_1234
modulo_returns_remainder
getter_returns_set_value
test_user_service_method_1
```

**Тестовые данные** — конкретные значения, не плейсхолдеры. Длинное или повторяющееся значение → фикстура или константа в начале файла.

**Моки** — только там, где они защищают инвариант от внешней зависимости (HTTP-клиент, БД в unit-тесте, время). Не мокать быстрое и детерминированное.

**Один тест — один инвариант.** Не запихивать несколько инвариантов в один тест ради экономии строк.

## Шаг 5. Что НЕ писать

- Тесты на удалённый функционал. Фича удалила старую кнопку → тест «старая кнопка отсутствует» делает прошлое вечным законом. Удали старые тесты, относящиеся к удалённой кнопке.
- Тесты на гарантированное системой типов: «функция, объявленная как `int -> int`, возвращает int». Тип уже гарантирует.
- Тесты на стандартную библиотеку: `assert (a + b) == (b + a)` для коммутативности сложения.
- Тесты на тривиальные геттеры/сеттеры: «положили значение в setter, getter вернул то же».
- Тесты, имя которых ссылается на номер бага или коммита (`fixes_bug_1234`).
- Покрытие ради покрытия: тривиальная строка кода не нуждается в отдельном кейсе.
- Лишние сценарии для простых фич. Минимум тестов — лучше.

## Шаг 6. Финальные действия по тестам

Файлы кода тестов записаны в `test_dir`. Не запускай тесты автоматически — решение пользователя.

В отчёте пользователю (этап 6 SKILL.md) укажи:
- сколько тест-файлов создано / изменено;
- сколько тест-кейсов всего;
- какие инварианты осознанно не покрыты и почему;
- команду `test_run_command` для прогона (если известна).

## Что НЕ делать

- Не редактировать `tests.md` — он финализирован стадией `test-plan`.
- Не делать git-операций.
- Не править код самой фичи. Для теста нужно сделать что-то более тестируемым → отметь как блокер в отчёте; пользователь решит.
