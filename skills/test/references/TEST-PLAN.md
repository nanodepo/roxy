# Стадия 2: Test Plan

> Когда читать: при запуске режима `test-plan` или как вторая стадия полного цикла.

Цель — превратить итог стадии `change-summary` в подробный план тестирования и записать в `./workflow/features/{slug}/tests.md`. Файл переписывается целиком; накопление дельт запрещено.

## Шаг 1. Подготовить вход

Стадия запущена сразу после `change-summary` (полный цикл) → итог уже в контексте.

Стадия запущена отдельно — итог `change-summary` отсутствует. Тогда:
1. Прочитай `feature.md`, `plan.md`, `NN-task.md`, текущий `tests.md` (если есть).
2. Проведи анализ через `mcp__sequential-thinking__sequentialthinking` по разделам стадии 1 (`references/CHANGE-SUMMARY.md`).
3. Получи итог анализа в контексте.

`tests.md` существует → прочитай его. Используй как материал, не как основу: финал переписывает файл целиком.

## Шаг 2. Структурировать план

Через `mcp__sequential-thinking__sequentialthinking` спроектируй разделы:

**Цель тестирования** — одно предложение про продуктовую цель фичи и что защищаем тестами.

**Скоуп:**
- *в скоупе* — компоненты и сценарии, покрываемые тестами фичи;
- *вне скоупа* — осознанно не покрываемое и почему (тривиально, гарантировано типами, не относится к фиче).

**Типы тестов** — таблица применимых к фиче. Не все типы должны быть; пиши только осмысленные:

| Тип             | Приоритет     | Когда применять                                       |
|-----------------|---------------|-------------------------------------------------------|
| Functional      | High          | Всегда — основная логика изменений                    |
| Regression      | Medium        | Смежная функциональность под риском                   |
| Edge cases      | Medium        | Граничные значения, нестандартные входы               |
| Negative        | Medium        | Невалидные данные, ошибки, отказы зависимостей        |
| Security        | High          | Затронута авторизация или пользовательские данные     |
| Performance     | Low           | Изменены запросы, алгоритмы, кеш                      |

**Тестовые данные** — конкретные примеры по категориям: валидные, граничные, невалидные, спец-случаи. Не «введите валидные данные», а конкретные значения.

**Преконды** — что должно быть в окружении для прогона: учётки, фикстуры, моки внешних сервисов.

**Критерии приёмки** — чек-лист условий, при которых фича покрыта тестами:
- все тесты приоритета `High` зелёные;
- ключевые регрессионные сценарии зелёные;
- негативные сценарии возвращают ожидаемые ошибки.

**Чек-лист проверок** — список инвариантов с приоритетами. Каждая строка — один продуктовый инвариант, защищаемый тестом. Имя — про инвариант, не про инцидент.

## Шаг 3. Сформировать `tests.md`

Шаблон (адаптируй под фичу — пропускай неприменимые разделы):

```markdown
# Tests: {название фичи}

## Цель тестирования

{Что защищаем тестами и почему.}

## Скоуп

**В скоупе:**
- {компонент / сценарий 1}
- {компонент / сценарий 2}

**Вне скоупа:**
- {что не покрываем и почему}

## Типы тестов

| Тип         | Приоритет | Область                   |
|-------------|-----------|---------------------------|
| Functional  | High      | {ядро изменений}          |
| Regression  | Medium    | {смежное}                 |
| Edge cases  | Medium    | {границы}                 |
| Negative    | Medium    | {ошибки}                  |

## Тестовые данные

| Категория      | Пример       | Назначение           |
|----------------|--------------|----------------------|
| Валидные       | {пример}     | Happy path           |
| Граничные      | {пример}     | Edge cases           |
| Невалидные     | {пример}     | Negative scenarios   |

## Преконды

- [ ] {окружение/данные/учётки}
- [ ] {моки внешних сервисов}

## Критерии приёмки

- [ ] Все High-приоритет тесты зелёные
- [ ] Регрессия по смежным сценариям зелёная
- [ ] Негативные сценарии возвращают ожидаемые ошибки

## Чек-лист инвариантов

| Инвариант                                                | Приоритет |
|----------------------------------------------------------|-----------|
| {guest_cannot_delete_project — гость не удаляет проект}  | High      |
| {billing_period_starts_on_first_business_day}            | High      |
| {checkout_requires_confirmed_payment_method}             | Medium    |
```

## Шаг 4. Записать `tests.md`

`Write ./workflow/features/{slug}/tests.md` — полное содержимое нового плана. Файл существовал → перезаписан целиком. Никаких блоков «было / стало», никаких упоминаний предыдущей версии.

## Что НЕ включать в `tests.md`

- Хронику изменений плана между запусками (`# 2026-05-14: добавлен раздел про edge cases`).
- Тесты на удалённый функционал (`старая кнопка отсутствует`).
- Тесты на возврат значения геттера, остаток от деления, проверку базовых типов — гарантированное языком/стандартной библиотекой.
- Сложные сценарии при простой фиче. Минимум тестов — лучше.

## Что НЕ делать на этой стадии

- Не писать код тестов; это стадия `test-cases`.
- Не запускать тесты.
- Не делать git-операций.
